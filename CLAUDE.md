# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A local client for [ArtifactsMMO](https://play.artifactsmmo.com/) (TypeScript + Preact, `@preact/signals` for state). **One Node service on this PC** (`src/server/main.ts`, run under `tsx`) runs the whole engine — queue runners, the hive, every call to the game API (`https://api.artifactsmmo.com`, Bearer token from `.env`) — and serves the browser UI, which is **only a view**. Moved off the browser tab 2026-11-05 after repeated Firefox tab OOM crashes; GitHub Pages was dropped.

## Commands

```bash
npm start          # vite build, then scripts/serve.mjs runs the service on http://localhost:5173/ (serves dist/)
npm run dev        # serve.mjs --watch: Vite (HMR) inside the service; engine .ts edits restart the service
npm run build      # UI production build → dist/
npm run typecheck  # tsc --noEmit (src/ and scripts/)
npm run check      # every scripts/check-*.mts + every runner scenario, offline, ~3 s; `npm run check -- <name>` runs one and prints its action trace
npm run assets     # bash scripts/download-assets.sh — re-download public/assets/ icons+tiles
node scripts/fetch-data.mjs       # new season: re-snapshot public/data/*.json from the live API
node scripts/fetch-map-assets.mjs # then fetch new map tiles (+ npm run assets for new icons)
npm run atlas      # ~5 min offline sim sweep → public/data/atlas.json (the Roadmap tab's data); re-run after fetch-data or a sim/BIS change
```

There is no test framework. The correctness gate is `npm run typecheck` + `npm run check` (+ `npm run build` for UI changes). `npm run check` (`scripts/check.mts`) runs each check in its own Node process with fresh scratch storage in the temp dir — never `.ammo/`. **Runner scenarios** (`scripts/scenarios/*.mts`, API in `scripts/harness/index.mts`) boot the real engine through `boot()` against a fake game behind `fetch` (`scripts/harness/fake.mts`: a world of characters + bank, actions with the game's response shapes and error codes, fault injection) on a virtual clock (`scripts/harness/clock.mts`), run queues to the end and assert on the world, the action trace and the queue; every scenario ends with a mirror check (engine state = the fake's world). A scenario marked `known: "<audit ref>"` reproduces a recorded defect: it must fail ("known defect reproduced"), and the run fails once it passes until the marker is removed. Three more checks run on every scenario: the mirror check above, the bounce check (a withdraw of a code followed by a deposit of it with only moves between fails the scenario unless it declares `bounces: true`) and the layer check (any action the fake answers 598 — the right x, y on the wrong layer — fails the scenario unless it declares `expect598: true`). The fake walks `move` on its own path-finding (596 blocked, 595 no path, 5 s per map crossed) and has `transition` with its conditions; it has no XP/levels and no task / recycle actions (`use` covers food only; achievements, pending rewards + `claim_item` and the altar's `offering` actions answer from what the scenario wrote) — an unimplemented call ends the scenario with an error. `ScenarioDef.planner` sets the planner's config before boot; `t.restart()` boots a second engine in a new process on the same storage and world (planner-restart). To smoke-test the service without disturbing the real one, run it on a spare port with throwaway storage: `PORT=5199 node --import tsx --experimental-webstorage --localstorage-file=<scratch>/test.db --disable-warning=ExperimentalWarning src/server/main.ts` (it syncs once with the `.env` token; with no queues it makes no actions), then curl `/events` + `/rpc` or drive it with puppeteer-core.

**Dev forensics**: the service appends a trace of every API action (method, path, body, status), queue note change, head-item transition, activity-log entry, service start and failed rpc to `logs/dev.log` (gitignored; `src/lib/devlog.ts`, sink installed by `server/main.ts`; a per-process tag distinguishes service starts). Read it to debug runner behavior post-hoc — it is how the potion-brew bank livelock was caught.

## The local service: browser ↔ server split

The engine modules (`state/`, `api/`, `plan/`, `sim/`, `catalog/`) are loaded by BOTH sides — the browser for signals and pure helpers, the service for real — and `IS_SERVER` (`src/lib/remote.ts`, `typeof window === "undefined"`) decides what runs where. The rules:

- **The tab never runs the engine.** Runner modules hydrate from and persist to storage only `if (IS_SERVER)` (queue, hive, sim/validate); the hive observer effect is server-only (in a tab it would dispatch a second copy of every wave); `api()`/`getAllPages()` throw in the browser; the tab holds no token.
- **UI → server:** every engine function the UI calls starts with `if (!IS_SERVER) return rpc("name", [args]);` and its module ends with `expose({ name, … })`. In the tab the call becomes `POST /rpc {fn, args}` (it returns a Promise — UI callers must not use sync return values); on the server it is the real function, so internal callers keep sync semantics. `act()` in `api/actions.ts` is the one chokepoint for every action, so the `actions.*` the UI calls need no wrappers of their own. **A new UI-called mutator needs the guard + expose, or it silently runs against the tab's mirror.**
- **Server → UI:** `SYNCED` in `src/state/synced.ts` lists every server-owned signal the UI reads; the service sends a snapshot on `GET /events` (SSE), then each changed one (50 ms coalesced; flushed before every rpc reply). `connect()` (from `main.tsx`) mirrors them and loads the catalog. **A new server-owned signal the UI shows must be added to `SYNCED`; the UI must never write one** (the next push overwrites it — e.g. a claimed reward is dropped in `apply.ts`, not in the drawer). Pure UI state (`selectedCharacter`, `route`, `panelTarget`, `hiveProposals`, …) stays local.
- **Storage:** Node's built-in `localStorage` (`--experimental-webstorage --localstorage-file=.ammo/storage.db`, SQLite, ~10 MB quota), so the engine's persistence code is unchanged. Token: `.env` `TOKEN` seeds `ammo:v1:token` when none is stored. One-time migration: a brand-new service (no `ammo:server:imported` marker, no queues) accepts `importLocal` from a tab that still has browser-era `ammo:*` keys, then exits so the supervisor restarts it into the imported queues (`ammo:v1:migrated` in the browser stops re-imports).
- **Process:** `scripts/serve.mjs` supervises — restarts on exit with a doubling delay (1 s → 5 min; every start costs a boot sync, so a crash loop must not spin), exit code 3 (port busy) is final, `--watch` restarts on `src/**/*.ts` changes (`.tsx`/`.css` are Vite HMR only). The service binds `127.0.0.1:5173` BEFORE `boot()` (a second copy dies before it could run a second set of runners), exits when the supervisor's IPC channel closes (no orphans), and logs rather than dies on unhandled rejections. `/events` + `/rpc` reject non-local `Host`/`Origin`; `/rpc` requires `application/json` (cross-site requests need a preflight the service never answers) — whoever can call `/rpc` plays the account.

## The core invariant: one sync, then no polling

This is the whole design and the thing most likely to be violated by accident. Read `src/state/sync.ts` and `src/state/apply.ts` together.

- At service start (`server/main.ts` → `boot()` in `sync.ts`): restore from storage, load static catalogs from `public/data/*.json` into memory, then do **exactly one** authoritative read of `/my/characters`, `/my/bank`, `/my/bank/items`, `/events/active`, `/my/pending_items` (unclaimed achievement payouts → 🎁 topbar badge + claim drawer; a claim's echo updates state, `apply.ts` drops the row — no re-read), account.
- **Time-limited map events** (`/events/active` → `activeEvents` signal in `store.ts`, helpers in `src/state/events.ts`): fetched in that sync and then by **the one standing poll** — `refreshEvents` in sync.ts, every 5 min, every 2 min while the planner's characters have event-gated demand open (task 013, `eventorders.ts eventPollMs`): events can't be seen in action echoes, spawn about daily (a 1/rate chance per minute while not up; the log of 11-17 to 11-20 holds 33 spawns where the docs expect 54, so the planner's mean gap is `SPAWN_LOG` 1.64 × (rate + duration)) for 60–90 min, and `/events/active` is a public DATA endpoint (2,000/h per IP — 12 or 30 an hour never touch the 300/h account bucket; the realtime websocket that pushes `event_spawn` is members-only and the account isn't one). New spawns are logged (⚡). Each event's expiration is enforced **locally** by the 4 Hz clock. Event tiles overlay the static map everywhere — MapView drawing/hover/click, `liveTileAt`, `nearest()` in loopkit, and the queue's fight/gather pickers (`availableMonsters`/`availableResources`, tagged ⚡).
- **Event standing orders** (`src/plan/events.ts` pure + `src/state/eventorders.ts` runtime, `reactToEvents` after every sync/poll): each live spawn (`eventKey` = code@created_at, handled set persisted in `ammo:v1:eventOrders`, mirrored as the synced `eventPlans` shown on Fleet's "Needs you" event rows) gets ONE trip put AHEAD of a free running queue's head (not a `prepare`, not already on a trip), like the daily offerings trigger. Merchants (nearest free character): sell the `SELL_FLOORS` whitelist above its floor (sap 300, shell 50, golden shrimp/egg 0 — gear is never sold; `partial` sells complete when stock runs out), then buy the `WISHLIST` — one `lost_world_map` per Lv 20+ character (pinned); backpacks are no longer bought (2026-11-18) — from bank gold + the sales minus `GOLD_FLOOR` (20k), stopping at the first wish it can't fully pay for. Monster events, for characters the planner does NOT own: the fastest SAFE owned-gear win fights ∞; resource events: the highest skill gathers ∞ — both end by the missing-map-target skip. Trip items carry `ev:*` ids, which 🔁 never recycles. Nobody free = retried next poll; nothing worth doing = "nothing to do". `scripts/check-events.mts`. **The planner's characters (task 013)**: a monster or resource spawn's members come from the core (`src/plan/planner/events.ts eventPlans` → `eventMembers`) at every poll while it is up, after the first achievements read; each member gets `interrupt(name, "event", tripOf(…), eventKey)` = [bank reset into the set for the work, fight or gather ×∞, the step underneath's own bank reset (else deposit-all)]; one `plan: event …` dev-log line per spawn (the demand, the members, every other owned character's reason), one more when someone joins later.
- After that, **nothing polls** the account. Every action endpoint echoes the full authoritative `character` (and bank item moves echo `bank`), so `applyActionResult` (`src/state/apply.ts`) is the single chokepoint that folds responses into state — no GET-after-write. Re-sync only on the manual Refresh button (`reconcile()`).
- Budgets to respect: per-account **read** endpoints are the scarcest (~300/hr) — never add polling/GET loops. Actions are ~2000/hr; automation loops are paced by the cooldown each action returns, which keeps them well under.

`src/api/client.ts` is the only place that does `fetch` to the game API (the tab's only fetches are `/rpc` in `lib/remote.ts` and the catalog files). It handles 429 (rate-limit) and 499 (still-on-cooldown) retries, transient network failures (transport-level backoff, 2s→30s over ~90s, then a code-0 ApiError — which the queue runner holds-and-retries on instead of pausing), and pagination, and returns the unwrapped `data`. New API calls go through `api()` / typed wrappers in `src/api/actions.ts`, which route every response through `applyActionResult`.

## State

`src/state/store.ts` holds all dynamic state as `@preact/signals` (`characters`, `bankItems`, `bankDetails`, `selectedCharacter`, `panelTarget`, a 4 Hz `now` clock for cooldown countdowns, etc.). Components read signals directly and re-render automatically. `src/state/persist.ts` mirrors the durable signals to the service's `localStorage` (key `ammo:v1:state`) so a restart resumes instantly.

## The automation runner (the queue)

Exactly **one** per-character async runner executes everything: the **queue** (`src/state/queue.ts` + item vocabulary in `src/plan/queue.ts`), driven entirely by action cooldowns (`setTimeout` chains) — **it runs in the local service; closing the browser tab doesn't touch it.**

A queue is a user-editable ordered list of simple actions (move / fight ×N / gather ×N / craft ×N / withdraw / gear / accept-task / work-task / deliver / turn-in / …). `work-task` works whatever the CURRENT task turns out to be (unknown until accept-task runs): a bank-reset gear swap once per task (`geared` remembers it), then fight the task monster, or acquire the task item in the field — gather it, or gather materials + craft — handing bagfuls straight to the items master; task stock never moves through the bank (`deliver` is the from-bank-stock alternative) — EXCEPT at a dead end (`giveUpTask`: no field source, no winnable set): bank stock is handed over, then the task is **cancelled** for a tasks coin (fetched from the bank when not in hand), and only with no coin anywhere does the queue pause. `task-loop` chains accept → work-task → turn-in as ONE repeating item (×N tasks, 0 = forever) — `done` counts turn-ins, `geared` re-arms the bank-reset gear swap per new task. Fight, gather and craft items with a count of `0` run **forever** (craft ∞ = withdraw-a-bagful → craft → deposit cycles until the bank can't feed the recipe); a craft with `wait` (hive pipelining) holds and re-polls instead of pausing when bag + bank can't feed one run. Every item is skip-if-satisfied, so reloads resume mid-item; failure **pauses** the queue with the error on the head item — EXCEPT a missing map target (monster/resource/shop/workshop/master not on the map, e.g. an expired event): that **skips** the item with a log line (`skipItem`) so queues survive events ending. Multi-character bank races never pause either: a withdraw hitting 404/478 (a sibling took the stock first) drops the code from the local `bankItems` signal and re-plans next tick (`gearSwapStep` + `runStep` in exec.ts), and 461 (concurrent bank transaction) is waited out inside `api()` like a cooldown. A 486 ("an action is already in progress" — the answer to the retry after a server 500) is held 5 s and retried up to 6 times in `runLoop` before it pauses. Only an outage is held 60 s and retried (`isOutage`: code 0 from the transport, or a code ≥ 500 that `docs/api/openapi.json` does not define — 500, 502, …); every code the document defines (595/596, 574–577, 550–573) is the game's answer and takes the ordinary error path, the pause text ending in `(code N)` — except 598 "not found on this map" at action time, a vanished target (task 008): the item runs once more and picks its tile again, a second 598 in a row skips it (`runOffering` still catches its own).

**Movement: layers and transitions (task 006, 2026-11-18).** The map has three layers (overworld / underground / interior) joined by 30 transition tiles. `src/plan/route.ts` (pure) builds regions once per catalog — tiles `move` travels between: never `blocked`; `restricted` only with restricted (the Enchanted Forest is entered by its toll transition); `conditional` a destination, never a corridor — and `route(from, to, may)` returns walk / transition legs through the transitions `may` opens: `FREE` (no conditions, 21 of 30) until keys and tolls come with the planner. `travelSec` = 5 s per map crossed (BFS path length) + 5 s per transition. In loopkit: `nearest(type, code, character)` considers only tiles with a route, ranked by travel time (event tiles on their own layer); `moveTo(name, place)` walks ONE leg per call and returns true once there (a route is interruptible between legs; callers re-derive the target every tick and check a full bag BEFORE walking toward work, so a bank trip of several legs never turns back); `walkTo` walks every leg for the one sequence that must not split (`giveUpTask`'s coin fetch + cancel); `isAt` compares x, y AND layer. No route = no candidate from `nearest` (the skip text from `missingText` says "only on another layer") or a `NoRouteError` from `moveTo` (runLoop skips the item). A queue item's persisted x, y without `layer` is on the overworld; `runStep` targets carry a `Place` (`at`). A `buy` item is done only when `npc/buy` succeeded: the purchase is recorded on the item (`bought`) the moment it happens and checked first on every tick, so the tick that withdraws the gold is not the purchase, and a step result discarded because the head changed, or a restart, never buys twice. Key `ammo:v1:queue`.

**Seasonal offerings (season 9, Seasonal Altar tile)**: the `offering` item does today's offerings — read `/my/{name}/offerings` once per character per UTC day (`todayOfferings`/`loadOfferings` in `src/state/offerings.ts`, cache `offerings` in store.ts, persisted, folded from accept/complete echoes in apply.ts — never polled), then at the altar accept every category (combat + 2 rotating skills) for the character's level bracket FIRST (the favor ×1.5 xp/drops boosts the farming) — but only one it can complete: `canObtainOffering` dry-runs the same sources (bank, favored target — or another monster with the drop when the favored one is off the map — field source, fight sim for drops); brackets above 10–20 ask for the TOP-of-bracket item (21–30 wants Lv 30 gold ore / cooked rat meat), so `offeringPick` falls back to the next LOWER bracket that is feasible (the reward is a % of the character's current level XP either way; the game accepts a lower bracket — confirmed 2026-11-18, mining 24 took mining_10_20), and only with none left is the category skipped for the day un-accepted (`scripts/check-offering.mts`), get each requirement (bank → favored target → field source, two craft levels deep; a craft offering never takes its product from the bank — banked gear is the fleet's), complete. A dead end skips that category for the day (`day`/`skip` on the item) instead of pausing; alone on a 🔁 queue a finished item holds for the next rotation instead of spinning. UI: Fleet 🛐 fold (`OfferingsSection`) + the altar drawer (`AltarPanel`, manual accept/complete). runOffering catches 574–577/598 itself (written when runLoop still held every code ≥ 500 as an outage). **Daily trigger** (`scheduleOfferings` in queue.ts, armed by `resumeQueue`): at 00:05 UTC (just after the midnight-UTC rotation — the API's `expires_at`) every RUNNING queue gets a fresh `offering` item AHEAD of its head, which resumes afterwards; a boot after 00:05 catches up once (marker `ammo:v1:offeringsDaily`); stopped/paused queues are left alone. Favors feed A Helping Hand (50 → 5 `altar_doll`, −10% gather + craft cooldown) and A Favored Champion (500 → 5 `altar_totem`, Lv 40).

**Per-character skill loops (2026-11-04, the main way to play; the hive is kept but frozen):** every character has up to two **pinned main skills** (`skillPins` in store.ts — click a row in the Skills card, 📌1/📌2, combat or any of the 8 skills, one more replaces the oldest; `craftPins()` hands the hive the first workshop pin). The `train` item levels a skill (`toLevel`, 0 = forever; `levels` = +N from the level it started at, `from` recorded on first run): **combat** fights the monster with the best XP per second (`trainingMonsterFor` in queue.ts: the docs' fight-XP formula `fightXp` in `plan/xp.ts` — level ratio + HP term, ×0.7 more than 5 levels above the monster, nothing more than 10 above (the gap rule the log shows, task 012: the pig gives XP to 29, none from 30), ×1.4 elite / ×2 boss — over 2 s/turn cooldown + rest-to-full, among monsters on the map the bank's best set beats; one BIS solve per candidate, memoized per bank reference + level; fed and gear-healed like a fight item; 📌 Train pins resets into the set vs the pick made at queue time), a gathering skill works the best node for the current level (re-picked per tick, `trainingResourceFor`), a workshop skill runs a self-contained loop in `runTrainCraft` — `trainRecipe` picks the recipe with the best **XP per fleet-second** (`src/plan/xp.ts`: the docs' crafting-XP formula — tier base by ITEM level, a √(ingredient count) multiplier, zero once the skill is 10+ above the item; cost = gather cooldown × drop rate per unit, a one-deep smelt of gathers, or a winnable drop fight at ~40 s × rate — `canBeat`, a bank-pool BIS solve memoized per bank reference — minus recycling's floor((n−1)/5)+1 random units back; an ingredient nobody can produce counts as free while bag + bank cover a run and caps the batch at that stock; stock on hand is already paid for — over one batch only the runs `stockOf` can't cover are charged field time, so banked materials get used first; `scripts/check-assist.mts`). The craft itself is ~5 s; materials are 99% of the time, so the model's whole point is XP per material unit and **every workshop recipe from Lv 10 up needs a monster drop** (feathers 1/8, slimeballs 1/10, cowhide/wool 1/12 — a drop costs about what a smelted bar costs). A batch is half a bag of DIRECT materials (6 bars per axe — a one-deep sub-craft is staged through the free half a bagful at a time, so 48 bars' 480 ore never has to fit at once), `sourceOne` fills a short ingredient (bank → gather → hunt, `fightGear` wears the bank's fight set → sub-craft), craft (weapon slot swapped to the best `<skill>_crafting` tool first — `craftGear`; it ping-pongs with the gathering tool as a bag-only equip because `trainKeep` holds spare tools), then recycle the product (or bank a non-recyclable one), repeat. **Automation never recycles a rare-ingredient product** (`autoRecyclable` in `plan/xp.ts`, 2026-11-09): recycling hands back random units, so a gem or tasks-coin crystal is mostly lost — an ingredient over `RARE_ACTIONS` (50) actions per unit from its cheapest source (best drop rate, a craft's ingredients summed, an NPC trade priced in drops; gold prices don't count) keeps the product banked for a manual decision, in the train picker (charged full materials), the train loop, the hive's level-skill batches and the recycling achievement. 157 of 257 recyclable recipes are gated that way (the whole jasper/astralyte tier), yet every craft skill keeps a common-only recipe at every level 1–50. The user's `recycle` queue item is untouched. `scripts/check-recycle.mts` asserts the split offline. **Helpers**: a `train` item with `for: <crafter>` ("help X train Y", the form's second select, or 🤝 **Fleet helps** = `queueAssist` puts one at the FRONT of every other queue and starts it) runs `runTrainAssist`: keep the bank two batches ahead on the crafter's CURRENT pick (the pick is fleet-aware — `helpersOf` = running queue heads helping that crafter, so a recipe only a helper can feed qualifies), produce one trip's load of the least-covered ingredient it can make (a bagful of raw smelted = 10 bars, at most a batch of a hunted drop — smelting never fills the bag, so a bigger load meant hours of bars riding in bags; finishing whatever is already in its bag first), deliver, repeat. Coverage (`assistPick`, 2026-11-17) = bank + banked RAW at the recipe's yield + every team bag (`stockOf`) + a full trip per OTHER helper already holding it — four helpers used to gather the same ash wood with 375 banked; near-ties go to an ingredient that levels the helper's pin. A helper never withdraws the ingredient itself, but does withdraw banked raw to refine (sourceOne's sub-craft is always bank-first); the crafter sources what it can itself and **waits** (15 s polls) for a helper-only ingredient instead of pausing. Fights in a train loop rest instead of eating (no food provisioning). A queue has a **🔁 repeat** flag (`QueueState.repeat`: a finished item goes to the back with its progress wiped; the hive clears it on dispatch so its ids can finish). **📌 Train pins** (`queuePinTraining`) builds the character's main task from the pins: per pin a bank-reset gear item + `train +1 level`, with 🔁 on, so the two skills level in turn forever.

These simple items are the **only execution vocabulary**. The old planner/campaign layer (goal compiler, task/train-craft phase machines, acquisition resolver) was removed 2026-07-06 — a planner must compile goals **down to queue items**, never run its own machinery. The hive (below) is that planner.

Stop semantics: ⏹ persists `running: false` IMMEDIATELY (a reload can never resurrect a stopped queue) while the loop drains its in-flight action — `liveLoops` covers that gap so ▶ during the drain just cancels the stop instead of double-launching. In dev the supervisor restarts the whole service on an engine edit (a hot swap would zombie the old runLoop); `queue.ts`/`hive.ts` still self-reload the TAB on HMR so its mirror signals stay single.

The runner pattern (copy it if a second runner ever returns): a `signal<Record<name, Job>>`, a module-level `stopFlags` Set, `step()` = run one action then `waitCooldownFull` (`src/state/loopkit.ts`), and the **reload-resume** pattern — the job signal is hydrated from its own `localStorage` key at module load, an `effect()` writes it back on change, and `resumeQueue()` (called from `boot()`/`login()` in `sync.ts` **after** the sync) re-launches. Hydrate before the persisting `effect` first runs or it overwrites the saved jobs — and both only `if (IS_SERVER)`. **Do not route runner persistence through `persist.ts`** (import cycle: `persist → queue → actions → apply → persist`) — the runner owns its key. Shared risky mechanics (bank-off, food-first healing, forecast gating, gear swaps) live once in `src/state/exec.ts`.

## The hive: the account-goal coordinator

The strategy layer above the queues — a **pure compiler + signal observer**, never a second execution engine. Domain in `src/plan/hive/` (pure functions over a `HiveCtx` snapshot: no signals, no API, no `state/` imports), runtime in `src/state/hive.ts`, UI in `src/ui/HivePanel.tsx` (🐝 topbar drawer + status strip atop the Fleet tab).

- **Propose → launch → observe.** `proposeGoals` enumerates + scores account goals (gear-upgrade / farm-tasks / achievement / level-skill) as value-per-hour (`score.ts` holds every tunable); a goal whose PLAN is partial is discounted (near-miss candidates alone don't halve it), and prerequisites are promoted as standalone goals scored as the parent's value over the combined wall-clock (`promoteBlockers`). Estimates: `SEC_PER_ACTION` is measured (~30 s), task cost comes from tasks.json sizes (`actionsPerTask`), parallel work converts to wall-clock per participant (`wallActions`). Two more kinds are built by the user in the drawer's builders and never auto-proposed: **craft-order** ("make me N of X" — the fleet gathers in parallel, the pinned/qualified crafter finishes behind a bank barrier; satisfied when the fleet OWNS the ordered quantities) and **earn-gold** ("earn +N gold", `plan/hive/gold.ts` — each participant works its best gold-per-action LANE: gather+sell / bounded task batches / fight+sell, ranked from live ctx; waves end in deposit-all so `ctx.bankGold` is fresh at the barrier, sell quantities stay provably coverable — guaranteed rate-1 drops plus bank stock claimed by ONE character per code — and it is satisfied when bank + participant pocket gold reaches the target). The user Launches one; the hive **takes over** all non-opted-out characters' queues (stop + clear, behind a confirm), then only ever writes queue items and watches the `queues` signal (one `effect` → microtask-coalesced `tick`).
- **Recompile-at-barrier is the core contract**: `compileGoal` returns waves but only `waves[0]` executes; when its assignments complete, the runtime re-calls `compileGoal` with fresh state and dispatches the NEW wave 0 — drop shortfalls become top-up waves, a consumer craft **pipelines** behind its producers in the same wave as a `wait` craft (holds and re-polls bag + bank instead of pausing on missing mats; `releaseStarved` drops one once no producer is left, so the barrier tops up), and skill training re-picks its recipe as the level rises. `HivePlan.once` (farm-tasks) means "wave done = goal done, no recompile"; an item-identical recompiled wave trips the **stall guard** (finish `incomplete`) — unless the plan's `progress` metric moved (earn-gold reports fleet gold there: a capped lane may honestly repeat the same batch while still earning; a zero-progress identical wave still stalls). Waves must contain **no infinite items** (they'd never complete) and ≤1 assignment per character — compile-side rules: mid-wave idle is rebalanced at **runtime** instead (`rebalanceWave`): a participant whose part is done (or who was never assigned, or who only holds on a starved `wait` craft — its slice is dispatched AHEAD of the craft via the hive-only `insertItem`, and it never gets a filler) first **steals** — `planSteal` carves half of the biggest running gather/fight lane they can work (a `times` patch on the victim's hive item via `patchItem`; a smelt chained right behind the gather moves with its ore in whole runs; never below `SPLIT_ACTIONS` × 30 s, never from a paused lane — slice and wave-tail sizes are SECONDS at each lane's measured pace (`lanePace`: elapsed since dispatch per fight/gather done, so eat/rest/food runs count; a wolf ran ~130 s, not 30), never a random-drop or two-deep chain) and gets the slice as a fresh barrier-holding assignment (ids in the `s<k>` namespace); only when nothing is carvable AND the wave's longest lane outlasts a gear reset (`FILLER_MIN_WAIT`) do they get an infinite `filler` assignment (`fillerItems` in tasks.ts: a `train` of their pinned gathering/combat skill — those only add to the bank, a workshop pin would draw on the wave's materials — else a task-loop at their best-suited master) — excluded from `waveDone`, item ids in the `f` namespace, dispatched only onto an empty stopped queue (user edits win), pulled (`pullFillers`) only when the run continues to a next wave so filler never delays the goal. A goal that ENDS (done/incomplete — not ⏹ stop) never parks the fleet (`moveOn`): the next **backlog** goal launches (user-queued via ＋ Queue; unlaunchable entries are dropped with a log line), else in **continuous mode** (⟳ chip, `auto`) the best proposal that compiles — minus labels that recently ended `incomplete`, so a stalling goal can't relaunch itself — else `handOffToTasks` sends every idle participant back to its 📌 pinned training (`queuePinTraining`; before 2026-11-17 it was a hard-coded items task-loop — 59% of fleet time went to shrimp tasks), or with no pins an infinite task-loop at its `taskSuitability` master, as plain user-owned items (fresh ids, not `hive:*`). Farm-tasks proposals stop once the bank holds `SCORE.COIN_RESERVE` (300) coins and the Tasks Trader is open. An auto-launch keeps user items on participants' queues (the hive appends behind them); only the manual Launch, behind its confirm, clears. ⏹ switches continuous mode off.
- **Dispatch is idempotent** via deterministic item ids (`hive:<startedAt>:<waveSeq>:<char>:<i>`): reloads re-attach instead of re-pushing, and a user deleting a hive item counts as done — the hive appends and watches; user edits win. Per-assignment status is **derived** from the queues signal (`assignmentStatus`: done = our ids gone, paused = error on OUR item, blocked = error on a user item ahead), never stored. A paused assignment holds its wave (others keep working) and gets Retry/Skip in the UI — no auto-retry.
- **Budget**: the hive itself performs ZERO API calls except one `loadAchievements()` per barrier for achievement goals (dynamic import of sync.ts keeps the static graph acyclic). `fleetBis` (ctx.ts) memoizes BIS searches per bank array reference with planning-grade pool caps; a cold `proposeGoals` is a 1–3 s synchronous sweep behind an explicit button.
- Follows the runner pattern: own key `ammo:v1:hive` (hydrate before the persisting effect, NOT via persist.ts), `resumeHive()` from `boot()`/`login()` **after** `resumeQueue()`, stop-sticks-first (`status:"stopped"` persists before queues unwind), HMR self-reload.
- `planAcquire`/`acquireWaves` (`plan/hive/acquire.ts`) is the rebuilt acquisition resolver — fleet-aware (gather → craft → fight → buy, candidates by skill/forecast, virtual-bank accounting, gather→smelt chains stay in one queue; every other craft pipelines in wave 0 on its preferred crafter as a `wait` craft, and a craft whose skill is PINNED to a specialist is never chained onto gatherers — the specialist gets the craft and its XP). Dead ends surface as `Blocker`s with a suggested prerequisite goal (small skill gap → level-skill, tasks_coin shortage → farm-tasks).

## The gear model: bank reset, bank-only sets

Gear is **never crafted or acquired for a character** — the bank is the single source of truth. Read `src/plan/jobgear.ts` (planner + stateless differ) with `gearSwapStep` in `src/state/exec.ts`.

- **A gear-managed job starts with a full bank reset**: go to the bank, deposit EVERYTHING (whole inventory, all pocket gold, every worn slot incl. utility potion stacks), then withdraw + equip the best set **available in the bank at that moment** (`jobGear`: fights via the bank-only BIS solver, gather/craft via prospecting/wisdom/tool argmax, plus a non-tool cooldown cut like `altar_doll` — `scripts/check-doll.mts`). Implemented as the `reset` mode of `nextGearAction`; the queue's `gear` item carries `reset: true`.
- **Fight sets include utility potions**: the BIS search covers the utility slots from owned stock (restore/boost potions change the forecast honestly — the live gate sees worn stacks via `currentFighter`). The differ equips whole stacks (game cap 100) and re-fills a slot from the bank when it drains empty; non-fight desired maps leave utility slots unmanaged, and a reset merges `RESET_UTILITY_STRIP` as an **underlay** so a fight set's potion picks survive while other jobs strip them.
- **Potions get brewed when the bank runs out**: `brewablePotions` (consumables.ts) lists potions the character could produce (alchemy skill + every ingredient stocked or gatherable); jobGear runs a second BIS solve with them as `extraCandidates` and adopts the set **only on a material forecast gain** (win-flip / safe-flip / fewer seconds per kill) — the solver's fills-a-slot tiebreak alone must never send anyone on a brew expedition. The BIS objective (`bis.ts`, `killSeconds`) is **seconds per kill** — fight cooldown (2 s/turn) + rest back from the HP missing at the fight's end (1 s per 1% of max HP, the docs and the log — task 012; it was 5 HP/s) + every potion the fight drinks (`FightForecast.used`: a restore potion one a proc, any other one a fight) at what making another takes (`potionSec`, `src/plan/xp.ts`; task 010) — an ingredient the stock holds for 100 runs of the recipe free (`potionPriceOf`, task 012: the executor's solves pass the bank they are given, the planner `available`) — never HP remaining: a restore potion heals every turn under half health, so an HP objective rewarded a slow weapon that dragged fights out (2026-11-07: fire staff over iron sword vs cow; a longer fight now drinks more potions), and rest-to-full alone let the potion pin end-of-fight HP at half of max, so every +HP armor read as extra rest and the solver stripped body armor (2026-11-08; armor now saves procs). `scripts/check-planner.mts` keeps both traps. `provisionPotions` (exec.ts, called from the fight item and taskGear after the swap converges) then brews a batch sized by the forecast — the units a fight drinks × the item's fights left, at most `BREW_MAX` (45) — via the shared `produceOnce` machinery, and the next gear tick equips it.
- Mid-job bank trips (inventory full) deposit loot + gold but keep worn gear (`depositAll`/`bankOff`). **A gear swap is not a bank-off** (2026-11-18; it used to sweep the whole bag whenever it stood on a bank tile, so anything a sourcing path had just withdrawn and its `keep` list did not name went straight back — raw beef, the tasks coin, a helper's ore for 7 hours). Outside a reset, `nextGearAction` deposits only junk gear (replaced, or wanted by no slot — at the bank, never a trip of its own) and, on the bank tile, exactly the room the swap itself needs (`roomOf`: a strip, a withdrawal or a bag change that would not fit; never `keep`, never an unmet want). Loot leaves the bag through `bankOff` when the bag is full, and through resets. The harness fails any scenario with a **bounce** (a withdraw of a code, then a deposit of it with only moves between).
- **Per-iteration self-heal**: fight/gather rounds re-derive the desired set from the live bank signal (memoized per bank reference — free until a bank echo changes it) and swap when something better appears.
- **Between-fight food is self-provisioned** (fight / work-task / task-loop items, `food: false` on a fight item opts out): a hurt fighter eats the best food in hand (`healOnce`), and when the hand runs dry `provisionFood` (exec.ts, plan side in `src/plan/consumables.ts`) sources more — withdraw the best stocked bank food, else **cook** the best recipe the stock can feed, else **gather** the raw materials in the field and cook them — only when that beats resting (`gatherPays`: the run's heal ≥ 1.25× the rest its gather time buys; rest is 5 HP/s here (`restSeconds` at its 500-HP default — task 012 left `gatherPays` on it), a gather ~30 s, so gudgeon/shrimp/trout lose and fishing for food starts at bass); a food that is another recipe's ingredient (apple → apple pie, coconut/lava fish → potions) is never eaten or picked (`healingFoods`), and an ingredient that feeds a gear recipe is never cooked (`gearMaterial`: mushroom → life ring / mushmush gear, so no mushroom soup — fighters ate a hive order's mushrooms); `scripts/check-food.mts` asserts this offline; batch sized by the fight forecast's expected HP loss (capped at ⅓ bag). Infeasible ⇒ falls back to rest — food never pauses a queue. Carried food + its ingredients ride the `keep` list so bank-offs and gear resets don't stash them; the task deliverable is never eaten.
- **Pinned artifacts** (`PINNED_ARTIFACTS` in jobgear.ts: `novice_guide`, `lost_world_map` — wisdom +100, bought by the Nomadic Merchant standing order): once owned, every job set of a character that meets its conditions (novice_guide: level ≥ 10, lost_world_map: ≥ 20) includes one, and a worn copy is NEVER removed — the differ drops its slot from management entirely (even under a reset/stripAll), so it survives all swaps. Spare copies still deposit. Also: artifacts must be DISTINCT (game rule, 485 "already equipped") — jobGear's argmax and the differ both dedupe artifact codes.
- **Fleet gear coverage** (🛡 topbar drawer, `src/ui/GearCoveragePanel.tsx` over pure `src/plan/coverage.ts`): a read-only "virtual bank reset for everyone at once" — slot-groups × characters matrix of the level-best owned set each character would get from shared stock (item-level ranking, zero fight sims; tools and utility slots excluded, pinned artifacts stay with their wearer), plus missing-copy shortages (have/need; rings count ×2) and nobody-can-fill slots. The Sim playground's 🏦 "Best in bank" button is the fight-side sibling: the same owned-pool BIS solve the gear reset runs, for a chosen monster.
- `src/plan/acquire.ts` is now only the `npcForSell` catalog lookup (the full acquisition resolver went with the planner layer).

## The planner (task 008: Fifth is on)

Design: `docs/design/planner.md`. **Core** `src/plan/planner/` (pure): `decide(name, world)` picks the next ~90-minute step for one free character (rules 1–5 of A.2; since task 011 rule 4 ranks `config.first`, then a real candidate — objective, level, supply — that fits the deadline, then a filler that fits, then real by points per hour, then filler by points per hour, so a road that fits nothing takes the fallback's hours, never a fitting filler's; it always returns a step, else the fallback gather, passing over a blocked `fallback:<skill>`); `itemsOf(step, ch)` compiles it to ≤ 4 queue items with ids `pl:<step.key>:<i>`; `forward`/`outlook` play the rule to the deadline (not run by the service yet). **Runtime** `src/state/planner.ts` (server-only, key `ammo:v1:planner`, the SYNCED `planner` signal: `current`, `costs`, `blocked`, `strikes`, the config **patch** over `DEFAULTS`, `achievementsAt`).

- **Who is on**: `config.on`, `DEFAULTS.on = { Fifth: true }`; `setPlannerConfig(patch)` (guard + expose; the Character tab's 🧭 switch). `isOwned(name)` lives in `store.ts` (`plannerOn`) so queue.ts / hive.ts / eventorders.ts can read it without importing planner.ts. With nobody on the runtime does nothing. Switched on: the queue's items are logged and dropped, 🔁 off, onto the hive's opt-out list; switched off: the `pl:` items go, the queue is left empty and stopped.
- **One writer.** The planner is the only automatic writer of an owned queue; it writes through `insertItem`, `dropItem`, `runQueue`, `haltQueue`, `resetQueue` (queue.ts, not exposed). The tab's edit ops, `queuePinTraining`, `queueAssist`, `queueOfferings` and `toggleHiveManual` refuse an owned character with one log line. Anything ahead of a step goes through **`interrupt(name, cls, items, what)`**: ids `pl:int:<cls>:<what>:<i>`, ahead of the head, behind an interrupt of the same or a higher class (`group` › `event` › `merchant` › `offering` › `claim`). The daily offerings trigger (`setOwnedOfferings` hook), the event standing orders (`reactToEvents`; task 013: for a monster or resource spawn, every member the core's `eventMembers` names) and the `claim` item (a new achievement completion → pending rewards → claim at the bank, deposit) come in that way. A step is never inserted ahead. **Offerings (task 010)**: the planner keeps per owned character the offerings day (the date of the most recent 00:05 UTC) whose interrupt it issued (`PlannerState.offered`) and catches up — at the 00:05 trigger, at boot, at switch-on and on the five-minute tick (`catchUpOfferings`); a removed offering interrupt comes back an hour later, at most three times a day; the panel's "＋ Queue" / "＋ Queue for all" and the altar drawer's button issue the interrupt for an owned character (`queueOfferings` → the hook, before `refused`), and the panel shows the bracket `offeringPick` will take (run in the tab, memoised per bank snapshot).
- **The loop**: `resumePlanner()` after `resumeQueue()` (re-attach by ids / take over / decide after the first achievements read, ≤ 5 min wait); one microtask tick per queue write and a 5-minute heartbeat. A step ends when no `pl:<key>:` item is left → sample (`running s ÷ units` into `costs`; `level:` keys hold hours) → an achievements read after an objective's or filler's step (≤ 6 reads an hour) → decide. A paused step item, a stall (counter still for `max(20 min, 5 × unit)` of running time) or a step that ended with no unit → `blocked["<target>@<name>"]` 6 h (third time running: everyone, until the next UTC day or a level-up); a paused interrupt is removed. Brake (task 010, per target): a target this character started 6 times within 10 min is blocked for it for 30 min and the decision is made again (at most three times in one `start()`); 20 starts of any kind within 10 min block every candidate (the ceiling) → fallback.
- **Dev log** (`logs/dev.log`): `plan <name>: <step.key> (<as>, <units> units, <h> h) — <why>`, `plan <name>: interrupt <cls> — …`, `blocked <target> 6 h — <why>`, `sample <key> <s> s (n=…, estimate … s)`, `took over — dropped [<id>] …`, `re-attached …`, `handed back …`, `offering interrupt comes back at <hh:mm>Z (n of 3 today)`, `offering interrupt issued again (n of 3 today)`; defects: `queue found stopped — started`, `flapping — <target>: n starts in 10 min, blocked 30 min` (the ceiling: `flapping — 20 starts in 10 min, every candidate blocked …`); `plan: completed …`, `plan: slower than expected — …`, `claim <name>: …`.
- **The core's second round (task 009)**: roles are pinned in `DEFAULTS.roles` (they never follow levels); a combat level is priced by the character's own XP monster per level (`levelHoursEstimate(lane, L, world, ch)`), a far gate is walked to the first level with no XP source (the "wall") and gear is asked for there; a kill's level is solved (`winLevel`, ten levels at most). **Supply through the bank** (`supply.ts`): every craft/buy objective and gear piece has a bill of materials; a short code is a target — `src:<code>` (a gather or kill chunk, units are actions), `mat:<code>` (a craft from the bank, or a trade for an item currency) — compiled to `[reset, field item | craft | withdraw+buy, deposit-all]`, `Step.as` `"supply"`, scored by its parent's chain. **Gear by need** (`gear.ts`): a set of craftable pieces is made when `G + H1 ≤ 0.85 × H0` for the XP road (judged on its next ten levels, per fighter), an open kill objective (task 011: the fleet's work — what is left less the others' running steps on it, `H0` the best-placed character's hours, ∞ only when nobody that is on wins it safely, at most one need per objective: the least `G + H1`, ties to the name; `gearNeeds(world, name)` with the deciding character), or a gathering lane (a tool, still per role holder); `gear:<code>` is crafted by the role's holder, a short crafter gets `lvl:<lane>:<level>` with the piece's points; pieces with gold / tasks-coin / boss / raid materials are listed as rejected (task 013: an event-only material is priced by its calendar, not rejected — rejected only when nobody can ever be a member of its event). The pool a character plans gear with is the bank less the others' reserved `Step.wear`, plus its own; the solve caches (`reach.ts`) are keyed on that pool and serve a subset pool that still holds the set's pieces, bounded (`MEMO_CAP`). The forward model wears sets, banks drops and crafts, and makes gear. `config.risk` (`"safe"` default, `"win"` for the replay's row D only). The core never imports `hive/`, `roadmap.ts` or `state/`.
- **What a potion costs (task 010)**: the forecast says what a fight consumes (`FightForecast.used`: a restore potion one a proc, any other potion one a fight) and a consumed potion costs what making another takes (`potionSec`, `src/plan/xp.ts`: ingredients' field seconds + the craft ÷ the recipe's quantity; no recipe: the rest its heal buys, a floor) — in `killSeconds` (`bis.ts`), so in the solver's objective, every planner price (`cost.ts`, `gear.ts`, `supply.ts`) and the executor's choice of set alike; safe stays the first tier. The brew batch is what the item's remaining fights drink by the forecast, at most 45 (`exec.ts`). An active offering favor multiplies its target's XP in `pickMonster` / `pickNode` (`World.favors`, from today's offerings cache; the forward model drops them).
- **Calibration (task 011)**: what a pig fight drinks was the sets, not the simulator — on the sets the log shows the forecast says 4–5 small health potions a pig fight (Monte Carlo 3.5–4.05, the log 3.0–4.8), report 010's 6 came from the snapshot pool's set, and at today's price those sets win the pig safely with no potion at all; the simulator is unchanged. `src/sim/validate.ts` records per fight the potions the forecast drinks and the potions really drunk (the worn stacks before and after, from the fight's echo — `recordFight(prev, monster, fight, after)` from `apply.ts`), `simAccuracy` the fights with a potion and the median error (signed). `config.potionK` (default 1, not in the UI, the executor keeps 1) scales `potionSec` in every solve and price of the core (`reach.ts potionPrice`) — for the replay's rows only.
- **Prices (task 012)**: fight XP is the docs' formula with the gap rule the log shows — × 0.7 only MORE than 5 levels above the monster, nothing more than 10 above (the pig gives XP to 29, none from 30) — and the wisdom of the set the fight is planned with (`reach.ts setWisdom`: the solved set + a worn pinned artifact; the forward model the worn set's `wisdom`). Rest is 1 s per 1% of max HP (`sim/cost.ts restSeconds(hp, maxHp)`; `consumables.ts gatherPays` keeps the 500-HP default); `KILL_LOG` (0.88: most steps eat, and food is not modelled) is the median of measured ÷ the repaired estimate over every kill step of 11-19, printed by the check. A craft, trade or gear step costs its fixed seconds once a step (`cost.ts stepSec`: the walk to the bank, to the workshop or trader and back, `STEP_BANK_SEC` 42 s of bank moves) in `planMake`, `rank()`'s gear and supply plans, a bill's mat leaves and `makeHours`. **Stock is free**: one price (`xp.ts potionPriceOf`) — an ingredient covered for 100 runs costs nothing, otherwise its field seconds — for the solver, the core (`reach.ts potionPrice(world, name)` over `available`; the solve caches keyed on what is covered among the potions the pool holds) and the executor (`jobgear.ts`, its bank); `config.potionStock` 0 = the field price always (the replay's row C). The forward model drinks (`forward.ts drinksOf`: a kill step's potions leave the bank at its end — the brewed stack down to one unit, so the potion stays plannable as the executor brews more, then its ingredients — never what a running step reserved). The node of a `src:` gather is the character's (`pick.ts pickSource`: the least net seconds an item, × (1 − the XP share) for a role holder; kills likewise with combat), in-flight steps counted in items; `sourceFor` stays the static answer for gates and bills. A craft of a chain (a mat leaf or the objective's own) gated at a level nobody that may craft it has puts the road to it into the parent's hours (`supply.ts gateRoad`), the level is a candidate of the lane's role holders with the parent's score, and with no road the parent waits (`waitingOf`: "a level with no XP source on the way").
- **Events (task 013, `src/plan/planner/events.ts`)**: event work has one writer, the `event` interrupt — a target with an `event` gate is never a step (`rank()`), nor is an event-only material's `src:` leaf, nor an event input inside an objective's own step (`inStep`). A spawn counts when its content serves open demand (`eventDemand`): an open objective that kills its monster (or a drop of it) or gathers a drop of its node, and what an open parent's bill (objective parents, gear pieces) is short of of an event-only material from it; one action serves all, so the demand is the largest in actions; it "can still pay" when the achievement (a material's parent) completes by the deadline at this event's calendar with everybody that can ever be a member (`possibleMembers`: a node's skill or the lane's role; a safe win now or within ten levels by `winLevel`; a free route; no boss — a toll or key event has a layer gate, `targets.ts placeGates`). `eventMembers(event, world, busy)`: every owned character that is on, not in a group, not on another spawn's trip, not after 22:00 UTC with its offering open, meets the gate (a safe win from its pool, the node's level), reaches the tile with 15 min left after the walk and the reset — the one that brings the most actions first, each on the pool less the earlier members' sets, while the demand left exceeds what the members bring; two spawns at once: the better-scoring demand first (`eventPlans`). **An event in the score is a calendar** (`calendar`: whole spawns needed × the mean gap `gapSec` = (rate + duration) min × `SPAWN_LOG` 1.64, measured on the log): an event achievement sits behind its lane's level in a bundle (its hours the members' character-hours, it fits when road + calendar fit; the members at that level: a gathering lane's role holders, the fighters that win by then), a bill's event-only material adds its calendar to the parent's hours (`materialCal`; ∞ with nobody: the parent waits, and `waitingOf` says "an event" only then or when it does not fit), an event monster's kill objective has gear by need like any other. The forward model attends events by expectation (`sharesOf`/`stretch`: a member gives the share usable seconds ÷ mean gap of its time while the demand lasts; the step takes that much longer; the work is applied after it as a kill or gather step's — `Played.events`); `config.events` 0 (row E only, potionK's rules) makes an event a wall again. The runtime's World counts a running `ach:` step in flight only for what it still has to do (`worldOf`, settled point 9).
- **Checks**: the `planner-*` and `event-*` scenarios (`npm run check -- planner-picks-kill` …, `planner-supply-step`, `event-fleet-monster`, `planner-inflight-left`); `npm run check -- planner` prints the core's first steps, the first week, the made-up worlds, the invariants, and the five replay rows to the deadline (A default — stock is free, the fights drink, events attended by expectation; B potions free, C the field price always, D a win is enough; E no events, `config.events` 0 — report 012's row A, the anchor; run as five child processes) with the "safe: a wall or a price" tables, what a pig fight drinks (the log against the simulator), the potion table on the real sets, the by-products and every gear need, task 012's tables (fight XP against the log, the kill samples against the repaired estimate, a kill step's parts, healing as it is, a step's fixed cost, stock covered against the field price, the node and the gate), and task 013's (the spawns of the log against the docs, every logged spawn under the new rule, events in the score per code, what events add to the bundles and the bills, what the events cost: row A against row E); the plain `npm run check` plays the first week only (~2 min — the real-time backstop of `scripts/check.mts` is 5 min, 30 min for one named check).

## The fight simulator's effects

`src/sim/combat.ts` (`simulate`) models every solo-relevant combat effect; `src/sim/effects.ts` (`MODELED`) is the audit list and records the reading taken for each one the docs leave ambiguous (2026-11-17: antipoison, corrupted, protective bubble, sun shield, greed, frenzy, enchanted mirror, void drain — plus poison/burn now land at the start of the BEARER's first turn). Only `christmas_magic` (no item or monster carries it) is unmodeled; ally-only effects are `SOLO_NOOP`. Hits are cached per side and recomputed only when an effect changes them (`dynamic`), and the turn mechanics are module-level functions (no per-call closures): ~2 µs per fight, half the pre-2026-11-17 cost — keep it that way, BIS searches and the atlas call it hundreds of thousands of times. Plain fights compute exactly as before. The fight-log check (`sim/validate.ts`) is the arbiter of those readings; `scripts/check-effects.mts` pins each mechanic on synthetic fights.

## Static catalog

`public/data/*.json` is a committed snapshot of the game's static data (items, maps, monsters, resources, npcs, …). `src/catalog/` loads it once into typed `Map`s and exposes sync lookups (`item()`, `monster()`, `mapAt()`, `tileAt()`, `itemName()`, …) that safely return `undefined` before load. `public/assets/` (map tiles + icons, committed) is served locally; most `<img>`s fall back to the CDN via `assetFallback`, **but map tiles in `MapView` have no fallback** — they must ship in the build or the map renders blank.

## Running

Local only — no deploy, no CI. `npm start` for unattended play (built UI, supervised service), `npm run dev` while editing. Both use port 5173, so only one runs at a time. The UI bundle ships no token (`.env` is read by the service only); the base path is always `/`. Shared engine code must not use `import.meta.env` (undefined under tsx) — `lib/devlog.ts`, `lib/util.ts` and `catalog/load.ts` were de-Vited for that; `catalog/load.ts` takes a disk reader from the service via `setDataReader`.
