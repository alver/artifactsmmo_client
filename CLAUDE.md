# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A local client for [ArtifactsMMO](https://play.artifactsmmo.com/) (TypeScript + Preact, `@preact/signals` for state). **One Node service on this PC** (`src/server/main.ts`, run under `tsx`) runs the whole engine — queue runners, the planner, every call to the game API (`https://api.artifactsmmo.com`, Bearer token from `.env`) — and serves the browser UI, which is **only a view**. Moved off the browser tab 2026-11-05 after repeated Firefox tab OOM crashes; GitHub Pages was dropped.

## Commands

```bash
npm start          # vite build, then scripts/serve.mjs runs the service on http://localhost:5173/ (serves dist/)
npm run dev        # serve.mjs --watch: Vite (HMR) inside the service; engine .ts edits restart the service
npm run build      # UI production build → dist/
npm run typecheck  # tsc --noEmit (src/ and scripts/)
npm run check      # every scripts/check-*.mts + every runner scenario, offline, ~3 s; `npm run check -- <name>` runs one and prints its action trace
npm run journal    # the journal's tables (docs/journal.md): -- [--from <ISO>] [--to <ISO>] [--file <f.jsonl>], the last 24 h by default; read-only
npm run market     # the market read's tables (logs/market/, docs/journal.md "The market"): -- [--from] [--to] [--code a,b] [--all] [--file]; read-only
npm run outlook    # task 019: a day's snapshot (logs/world/, the newest by default) played to the deadline: -- [--world <file>] [--days N] [--json]; no service, writes nothing; task 027: this code's DEFAULTS under the snapshot's config patch
npm run assets     # bash scripts/download-assets.sh — re-download public/assets/ icons+tiles
node scripts/fetch-data.mjs       # new season: re-snapshot public/data/*.json from the live API
node scripts/fetch-map-assets.mjs # then fetch new map tiles (+ npm run assets for new icons)
npm run atlas      # ~5 min offline sim sweep → public/data/atlas.json (read by the planner's core and check-planner); re-run after fetch-data or a sim/BIS change
```

There is no test framework. The correctness gate is `npm run typecheck` + `npm run check` (+ `npm run build` for UI changes). `npm run check` (`scripts/check.mts`) runs each check in its own Node process with fresh scratch storage in the temp dir — never `.ammo/`. **Runner scenarios** (`scripts/scenarios/*.mts`, API in `scripts/harness/index.mts`) boot the real engine through `boot()` against a fake game behind `fetch` (`scripts/harness/fake.mts`: a world of characters + bank, actions with the game's response shapes and error codes, fault injection) on a virtual clock (`scripts/harness/clock.mts`), run queues to the end and assert on the world, the action trace and the queue; every scenario ends with a mirror check (engine state = the fake's world). A scenario marked `known: "<audit ref>"` reproduces a recorded defect: it must fail ("known defect reproduced"), and the run fails once it passes until the marker is removed. Three more checks run on every scenario: the mirror check above, the bounce check (a withdraw of a code followed by a deposit of it with only moves between fails the scenario unless it declares `bounces: true`) and the layer check (any action the fake answers 598 — the right x, y on the wrong layer — fails the scenario unless it declares `expect598: true`). The fake walks `move` on its own path-finding (596 blocked, 595 no path, 5 s per map crossed) and has `transition` with its conditions; it has no XP/levels and no task / recycle actions (`use` covers food only; achievements, pending rewards + `claim_item` and the altar's `offering` actions answer from what the scenario wrote) — an unimplemented call ends the scenario with an error. `ScenarioDef.planner` sets the planner's config before boot; `t.restart()` boots a second engine in a new process on the same storage and world (planner-restart). To smoke-test the service without disturbing the real one, run it on a spare port with throwaway storage: `PORT=5199 node --import tsx --experimental-webstorage --localstorage-file=<scratch>/test.db --disable-warning=ExperimentalWarning src/server/main.ts` (it syncs once with the `.env` token; with no queues it makes no actions), then curl `/events` + `/rpc` or drive it with puppeteer-core.

**Dev forensics**: the service appends a trace of every API action (method, path, body cut at 600 characters, status), queue note change, head-item transition, activity-log entry, service start and failed rpc — the raw log — to hourly files `logs/raw/<YYYY-MM-DD>/<HH>.log` by each line's own UTC time (gitignored; `src/lib/devlog.ts`, sinks in `src/lib/journal.ts fileSinks`, installed by `server/main.ts`; a per-process tag, the run id, distinguishes service starts). `logs/dev.log` is the archive to 2026-11-21. Read it to debug runner behavior post-hoc — it is how the potion-brew bank livelock was caught. **The journal (task 016, schema `docs/journal.md`)**: beside it, `logs/journal/<day>.jsonl` — one JSON record a line written by the runtime when the thing happens (`boot` with the commit, every `step` and its `end` with units, wall/running/planned seconds and **the meter**: per character, every action's echo's `cooldown.total_seconds` by its `reason` group — fight · rest · eat · bank · walk · gear · gather · craft · trade · task · other — plus `wait`, counts, XP, drops, potions drunk, food eaten, bank moves, cut at every step and interrupt boundary in `act()`; `int`/`int-end`, `block`, `flap`, `nostep`, `defect`, `stopped`, `sample`, `slow`, `event`, `bank`, `ach`, `level`, `pause`, `server`, `config`; task 017: `spend`; task 041: `sale`); `logs/status.json` rewritten every minute (older than two minutes = the service is down); `logs/world/<day>.json`, the day's World snapshot (`decide()` runs on it alone). `npm run journal` prints the tables a task's "read the log" section needs. A service on another port writes under `logs/port-<N>/`; the checks and the harness write no file (memory sinks: `t.journal()`, `t.files()`).

## The local service: browser ↔ server split

The engine modules (`state/`, `api/`, `plan/`, `sim/`, `catalog/`) are loaded by BOTH sides — the browser for signals and pure helpers, the service for real — and `IS_SERVER` (`src/lib/remote.ts`, `typeof window === "undefined"`) decides what runs where. The rules:

- **The tab never runs the engine.** Runner modules hydrate from and persist to storage only `if (IS_SERVER)` (queue, planner, event orders, sim/validate); `api()`/`getAllPages()` throw in the browser; the tab holds no token.
- **UI → server:** every engine function the UI calls starts with `if (!IS_SERVER) return rpc("name", [args]);` and its module ends with `expose({ name, … })`. In the tab the call becomes `POST /rpc {fn, args}` (it returns a Promise — UI callers must not use sync return values); on the server it is the real function, so internal callers keep sync semantics. `act()` in `api/actions.ts` is the one chokepoint for every action, so the `actions.*` the UI calls need no wrappers of their own. **A new UI-called mutator needs the guard + expose, or it silently runs against the tab's mirror.**
- **Server → UI:** `SYNCED` in `src/state/synced.ts` lists every server-owned signal the UI reads; the service sends a snapshot on `GET /events` (SSE), then each changed one (50 ms coalesced; flushed before every rpc reply). `connect()` (from `main.tsx`) mirrors them and loads the catalog. **A new server-owned signal the UI shows must be added to `SYNCED`; the UI must never write one** (the next push overwrites it — e.g. a claimed reward is dropped in `apply.ts`, not in the drawer). Pure UI state (`selectedCharacter`, `route`, `panelTarget`, …) stays local.
- **Storage:** Node's built-in `localStorage` (`--experimental-webstorage --localstorage-file=.ammo/storage.db`, SQLite, ~10 MB quota), so the engine's persistence code is unchanged. Token: `.env` `TOKEN` seeds `ammo:v1:token` when none is stored. One-time migration: a brand-new service (no `ammo:server:imported` marker, no queues) accepts `importLocal` from a tab that still has browser-era `ammo:*` keys, then exits so the supervisor restarts it into the imported queues (`ammo:v1:migrated` in the browser stops re-imports).
- **Process:** `scripts/serve.mjs` supervises — restarts on exit with a doubling delay (1 s → 5 min; every start costs a boot sync, so a crash loop must not spin), exit code 3 (port busy) is final, `--watch` restarts on `src/**/*.ts` changes (`.tsx`/`.css` are Vite HMR only). The service binds `127.0.0.1:5173` BEFORE `boot()` (a second copy dies before it could run a second set of runners), exits when the supervisor's IPC channel closes (no orphans), and logs rather than dies on unhandled rejections. `/events` + `/rpc` reject non-local `Host`/`Origin`; `/rpc` requires `application/json` (cross-site requests need a preflight the service never answers) — whoever can call `/rpc` plays the account.

## The core invariant: one sync, then no polling

## State

`src/state/store.ts` holds all dynamic state as `@preact/signals` (`characters`, `bankItems`, `bankDetails`, `selectedCharacter`, `panelTarget`, a 4 Hz `now` clock for cooldown countdowns, etc.). Components read signals directly and re-render automatically. `src/state/persist.ts` mirrors the durable signals to the service's `localStorage` (key `ammo:v1:state`) so a restart resumes instantly.

## The automation runner (the queue)

Exactly **one** per-character async runner executes everything: the **queue** (`src/state/queue.ts` + item vocabulary in `src/plan/queue.ts`), driven entirely by action cooldowns (`setTimeout` chains) — **it runs in the local service; closing the browser tab doesn't touch it.**

A queue is an ordered list of simple actions — fight ×N / gather ×N / craft ×N / withdraw / deposit-all / buy / sell / recycle / train (a crafting level) / gear / task-loop / task-visit (task 027d: one visit to the tasks master) / offering / prepare / claim / expand — written by the planner and the Group fight fold only (see "Who writes a queue" below; the tab edits nothing since task 018). `task-loop` chains accept → work the CURRENT task → turn in as ONE repeating item (×N tasks, 0 = forever; `runWorkTask`): a bank-reset gear swap once per task (`geared` remembers it, re-armed per new task), then fight the task monster, or acquire the task item in the field — gather it, or gather materials + craft — handing bagfuls straight to the items master; task stock never moves through the bank — EXCEPT at a dead end (`giveUpTask`: no field source, no winnable set): bank stock is handed over, then the task is **cancelled** for a tasks coin (fetched from the bank when not in hand), and only with no coin anywhere does the queue pause; `done` counts turn-ins. Fight, gather and craft items with a count of `0` run **forever** (craft ∞ = withdraw-a-bagful → craft → deposit cycles until the bank can't feed the recipe); a craft with `wait` (the deleted hive's pipelining, written by nobody now) holds and re-polls instead of pausing when bag + bank can't feed one run. Every item is skip-if-satisfied, so reloads resume mid-item; failure **pauses** the queue with the error on the head item — EXCEPT a missing map target (monster/resource/shop/workshop/master not on the map, e.g. an expired event): that **skips** the item with a log line (`skipItem`) so queues survive events ending. Multi-character bank races never pause either: a withdraw hitting 404/478 (a sibling took the stock first) drops the code from the local `bankItems` signal and re-plans next tick (`gearSwapStep` + `runStep` in exec.ts), and 461 (concurrent bank transaction) is waited out inside `api()` like a cooldown. A 486 ("an action is already in progress" — the answer to the retry after a server 500) is held 5 s and retried up to 6 times in `runLoop` before it pauses. Only an outage is held 60 s and retried (`isOutage`: code 0 from the transport, or a code ≥ 500 that `docs/api/openapi.json` does not define — 500, 502, …); every code the document defines (595/596, 574–577, 550–573) is the game's answer and takes the ordinary error path, the pause text ending in `(code N)` — except 598 "not found on this map" at action time, a vanished target (task 008): the item runs once more and picks its tile again, a second 598 in a row skips it (`runOffering` still catches its own).

**Movement: layers and transitions (task 006, 2026-11-18).** The map has three layers (overworld / underground / interior) joined by 30 transition tiles. `src/plan/route.ts` (pure) builds regions once per catalog — tiles `move` travels between: never `blocked`; `restricted` only with restricted (the Enchanted Forest is entered by its toll transition); `conditional` a destination, never a corridor — and `route(from, to, may)` returns walk / transition legs through the transitions `may` opens: `FREE` (no conditions, 21 of 30) for the planner's free questions; task 017: the runner's `mayFor(ch)` (loopkit) opens FREE plus every transition whose conditions the character meets now — the gold in its pocket (twice the fare where the way back is paid too: nobody is stranded), the key in its bag, the carried item in its bag or worn — and the core's `mayOf(world, name)` (reach.ts) every one the plan can meet: a key or carried item it may take, a fare the gold budget covers with the way back; `config.tolls` 0 = FREE everywhere. `travelSec` = 5 s per map crossed (BFS path length) + 5 s per transition. In loopkit: `nearest(type, code, character)` considers only tiles with a route, ranked by travel time (event tiles on their own layer); `moveTo(name, place)` walks ONE leg per call and returns true once there (a route is interruptible between legs; callers re-derive the target every tick and check a full bag BEFORE walking toward work, so a bank trip of several legs never turns back); `walkTo` walks every leg for the one sequence that must not split (`giveUpTask`'s coin fetch + cancel); `isAt` compares x, y AND layer. No route = no candidate from `nearest` (the skip text from `missingText` says "only on another layer") or a `NoRouteError` from `moveTo` (runLoop skips the item). A queue item's persisted x, y without `layer` is on the overworld; `runStep` targets carry a `Place` (`at`). A `buy` item is done only when `npc/buy` succeeded: the purchase is recorded on the item (`bought`) the moment it happens and checked first on every tick, so the tick that withdraws the gold is not the purchase, and a step result discarded because the head changed, or a restart, never buys twice. Key `ammo:v1:queue`.

**Seasonal offerings (season 9, Seasonal Altar tile)**: the `offering` item does today's offerings — read `/my/{name}/offerings` once per character per UTC day (`todayOfferings`/`loadOfferings` in `src/state/offerings.ts`, cache `offerings` in store.ts, persisted, folded from accept/complete echoes in apply.ts — never polled), then at the altar accept every category (combat + 2 rotating skills) for the character's level bracket FIRST (the favor ×1.5 xp/drops boosts the farming) — but only one it can complete: `canObtainOffering` dry-runs the same sources (bank, favored target — or another monster with the drop when the favored one is off the map — field source, fight sim for drops); brackets above 10–20 ask for the TOP-of-bracket item (21–30 wants Lv 30 gold ore / cooked rat meat), so `offeringPick` falls back to the next LOWER bracket that is feasible (the reward is a % of the character's current level XP either way; the game accepts a lower bracket — confirmed 2026-11-18, mining 24 took mining_10_20), and only with none left is the category skipped for the day un-accepted (`scripts/check-offering.mts`), get each requirement (bank → favored target → field source, two craft levels deep; a craft offering never takes its product from the bank — banked gear is the fleet's), complete. A batch is half a bag of DIRECT materials (6 bars per axe — a one-deep sub-craft is staged through the free half a bagful at a time, so 48 bars' 480 ore never has to fit at once), `sourceOne` fills a short ingredient (bank → gather → hunt, `fightGear` wears the one verdict's fight set — task 023: no brew set for an owned character, its stacks capped at what the bank may give, a hunt priced at its verdict's seconds a kill, fight + rest + potions, not `FIGHT_SEC` — → sub-craft), craft (weapon slot swapped to the best `<skill>_crafting` tool first — `craftGear`; it ping-pongs with the gathering tool as a bag-only equip because `trainKeep` holds spare tools), then recycle the product (or bank a non-recyclable one), repeat. These simple items are the **only execution vocabulary**. The old planner/campaign layer (goal compiler, task/train-craft phase machines, acquisition resolver) was removed 2026-07-06 — a planner must compile goals **down to queue items**, never run its own machinery. The planner (`src/plan/planner/`, `src/state/planner.ts`, below) is that planner.

Stop semantics: `haltQueue` (the planner's take-over and hand-back) persists `running: false` IMMEDIATELY (a reload can never resurrect a stopped queue) while the loop drains its in-flight action — `liveLoops` covers that gap so a `runQueue` during the drain just cancels the stop instead of double-launching. In dev the supervisor restarts the whole service on an engine edit (a hot swap would zombie the old runLoop); `queue.ts`/`planner.ts` still self-reload the TAB on HMR so its mirror signals stay single.

The runner pattern (copy it if a second runner ever returns): a `signal<Record<name, Job>>`, a module-level `stopFlags` Set, `step()` = run one action then `waitCooldownFull` (`src/state/loopkit.ts`; task 032, E: a cooldown is waited by the game's clock — `lib/util.ts cooldownLeft`, the local clock corrected by the skew of the latest echo, its `cooldown.started_at` less its arrival (`noteEcho` in `act()`); before a character's first echo of the run, by the local clock as before; scenario `cooldown-skew`, the fake's `world.skew`), and the **reload-resume** pattern — the job signal is hydrated from its own `localStorage` key at module load, an `effect()` writes it back on change, and `resumeQueue()` (called from `boot()`/`login()` in `sync.ts` **after** the sync) re-launches. Hydrate before the persisting `effect` first runs or it overwrites the saved jobs — and both only `if (IS_SERVER)`. **Do not route runner persistence through `persist.ts`** (import cycle: `persist → queue → actions → apply → persist`) — the runner owns its key. Shared risky mechanics (bank-off, food-first healing, forecast gating, gear swaps) live once in `src/state/exec.ts`.

## Who writes a queue (task 018)

Switched off (`setPlannerConfig({ on })`, the 🧭 button), its queue is emptied and stopped and it stands still. ## The gear model: bank reset, bank-only sets

Gear is **never crafted or acquired for a character** — the bank is the single source of truth. Read `src/plan/jobgear.ts` (planner + stateless differ) with `gearSwapStep` in `src/state/exec.ts`.

- **A gear-managed job starts with a full bank reset**: go to the bank, deposit EVERYTHING (whole inventory, all pocket gold, every worn slot incl. utility potion stacks), then withdraw + equip the best set **available in the bank at that moment** (`jobGear`: fights via the bank-only BIS solver, gather/craft via prospecting/wisdom/tool argmax, plus a non-tool cooldown cut like `altar_doll` — `scripts/check-doll.mts`). Implemented as the `reset` mode of `nextGearAction`; the queue's `gear` item carries `reset: true`.
- **Fight sets include utility potions**: the BIS search covers the utility slots from owned stock (restore/boost potions change the forecast honestly — the live gate sees worn stacks via `currentFighter`). The differ equips whole stacks (game cap 100) and re-fills a slot from the bank when it drains empty; non-fight desired maps leave utility slots unmanaged, and a reset merges `RESET_UTILITY_STRIP` as an **underlay** so a fight set's potion picks survive while other jobs strip them.
- **Potions get brewed when the bank runs out**: `brewablePotions` (consumables.ts) lists potions the character could produce (alchemy skill + every ingredient stocked or gatherable); jobGear runs a second BIS solve with them as `extraCandidates` and adopts the set **only on a material forecast gain** (win-flip / safe-flip / fewer seconds per kill) — the solver's fills-a-slot tiebreak alone must never send anyone on a brew expedition. The BIS objective (`bis.ts`, `killSeconds`) is **seconds per kill** — fight cooldown (2 s/turn) + rest back from the HP missing at the fight's end (1 s per 1% of max HP, the docs and the log — task 012; it was 5 HP/s) + every potion the fight drinks (`FightForecast.used`: a restore potion one a proc, any other one a fight) at what making another takes (`potionSec`, `src/plan/xp.ts`; task 010) — an ingredient the stock holds for 100 runs of the recipe free (`potionPriceOf`, task 012: the executor's solves pass the bank they are given, the planner `available`) — never HP remaining: a restore potion heals every turn under half health, so an HP objective rewarded a slow weapon that dragged fights out (2026-11-07: fire staff over iron sword vs cow; a longer fight now drinks more potions), and rest-to-full alone let the potion pin end-of-fight HP at half of max, so every +HP armor read as extra rest and the solver stripped body armor (2026-11-08; armor now saves procs). `scripts/check-planner.mts` keeps both traps. `provisionPotions` (exec.ts, called from the fight item and taskGear after the swap converges) then brews a batch sized by the forecast — the units a fight drinks × the item's fights left, at most `BREW_MAX` (45) — via the shared `produceOnce` machinery, and the next gear tick equips it. **Task 014: none of this for a character the planner owns** — its fight items carry `take` (the potions and food its step planned, `{}` when none) and the item tells the path apart: the solve counts as potions only the planned ones, free (`jobGear(…, planned)`), nothing is brewed, cooked or gathered inside the item, the step's reset puts exactly the planned quantity into the utility slots (`nextGearAction` opts `utility`: a worn stack of the same potion is topped up or trimmed, the top-up kept out of the reset's stash) and the planned food into the bag (the gear item of a `pl:` step reads the `take` of the fight item right behind it), a round never refills a utility slot from the bank, the next reset banks what is left, and an item whose potions or food are gone and whose fresh forecast is no win ends there (`ran dry …`, a completed item: sampled, never blocked); with the food gone it rests. The executor's choice for characters the planner does not own is today's.
- **One verdict (task 023, settled point 2)**: for an owned character whatever decides that a fight will be fought and the gate that admits it (`exec.ts fightRound`) judge the same set with the same stacks. `exec.ts fightSetFor(name, ch, monster, take?)` is the one memo (per character and job; keyed on the bank array, the others' reservations, the level — and re-solved when a utility stack the set named is gone: not worn, not in the bag, none the bank may give; settled point 2 (a)): the set and the forecast of exactly that set (`simulate` of its codes, what the gate sees once it is worn) and its seconds a kill (`jobgear.ts fightSeconds`). An owned character's fight outside a planned take — a train loop's hunt, an offering's, a task's — gets the best set of what it holds and the bank may give it (`ownedFightRec` on the bank less the running steps' reservations: `exec.ts freeQty`, the hook `setReservedOf` set in `eventorders.ts` from `stock.ts reserved` on the live World), never `jobGear`'s brew set; the swap's utility stacks are capped at what it wears and holds plus what the bank may give (`stackCaps`); nothing is brewed (`provisionPotions` only for a character the planner does not own) and nothing cooked or gathered (`ctxOf`: an owned offering's and task's fights eat what is in hand and rest). `queue.ts canBeat` for an owned character is that verdict's `win`, so a train loop's recipe whose drop it cannot win that way is not picked. Paths: a `pl:` fight step and an event trip wear their planned set (`plannedSet`) and their take; the offering's, the train loop's and the task's fights the verdict's set; `prepare` is refused for an owned character. Scenarios `train-hunt-verdict` (the train loop's hunt with a brewable potion nobody holds), `offering-drained-stack`.
- Mid-job bank trips (inventory full) deposit loot + gold but keep worn gear — and (task 027f) the gear a swap has just withdrawn to wear and not worn yet (`exec.ts toWear`, cleared when the swap converges): `bankOff` and the train item's and the task loop's own full-bag tests (`otherCargo`) leave it in the bag, so the next tick equips it — Fourth's train loop of 11-23 → 11-25 banked and withdrew its hunt's set 3,379 times; scenario `train-gear-loop` (`depositAll`/`bankOff`); a code the bank has no slot for stays in the bag (task 015: `loopkit.ts deposit`, the planner's section). **A gear swap is not a bank-off** (2026-11-18; it used to sweep the whole bag whenever it stood on a bank tile, so anything a sourcing path had just withdrawn and its `keep` list did not name went straight back — raw beef, the tasks coin, a helper's ore for 7 hours). Outside a reset, `nextGearAction` deposits only junk gear (replaced, or wanted by no slot — at the bank, never a trip of its own) and, on the bank tile, exactly the room the swap itself needs (`roomOf`: a strip, a withdrawal or a bag change that would not fit; never `keep`, never an unmet want). Loot leaves the bag through `bankOff` when the bag is full, and through resets. The harness fails any scenario with a **bounce** (a withdraw of a code, then a deposit of it with only moves between).
- **Per-iteration self-heal**: fight/gather rounds re-derive the desired set from the live bank signal (memoized per bank reference — free until a bank echo changes it) and swap when something better appears.
- **Between-fight food is self-provisioned** (fight / task-loop items, `food: false` on a fight item opts out): a hurt fighter eats the best food in hand (`healOnce`), and when the hand runs dry `provisionFood` (exec.ts, plan side in `src/plan/consumables.ts`) sources more — withdraw the best stocked bank food, else **cook** the best recipe the stock can feed, else **gather** the raw materials in the field and cook them — only when that beats resting (`gatherPays`: the run's heal ≥ 1.25× the rest its gather time buys; rest is 5 HP/s here (`restSeconds` at its 500-HP default — task 012 left `gatherPays` on it), a gather ~30 s, so gudgeon/shrimp/trout lose and fishing for food starts at bass); a food that is another recipe's ingredient (apple → apple pie, coconut/lava fish → potions) is never eaten or picked (`healingFoods`), and an ingredient that feeds a gear recipe is never cooked (`gearMaterial`: mushroom → life ring / mushmush gear, so no mushroom soup — fighters ate a hive order's mushrooms); `scripts/check-food.mts` asserts this offline; batch sized by the fight forecast's expected HP loss (capped at ⅓ bag). Infeasible ⇒ falls back to rest — food never pauses a queue. Carried food + its ingredients ride the `keep` list so bank-offs and gear resets don't stash them; the task deliverable is never eaten. **Task 014: a planner's fight item (`take`) does not provision** (`fed` false in `ctxOf`): it eats what its reset took (`healOnce`) and rests when that is gone — food for the owned characters is planned and cooked through the bank (the planner section); `gatherPays` and its 5 HP/s stay for the others' path.
- **Pinned artifacts** (`PINNED_ARTIFACTS` in jobgear.ts: `novice_guide`, `lost_world_map` — wisdom +100, bought by the Nomadic Merchant standing order): once owned, every job set of a character that meets its conditions (novice_guide: level ≥ 10, lost_world_map: ≥ 20) includes one, and a worn copy is NEVER removed — the differ drops its slot from management entirely (even under a reset/stripAll), so it survives all swaps. Spare copies still deposit. Also: artifacts must be DISTINCT (game rule, 485 "already equipped") — jobGear's argmax and the differ both dedupe artifact codes.
- **The Sim playground's 🏦 "Best in bank"** button runs the same owned-pool BIS solve the gear reset runs, for a chosen monster. (The Fleet gear coverage view, `src/plan/coverage.ts`, was deleted in task 018: the planner's gear by need is the one answer to "what does the fleet lack".)
- `src/plan/acquire.ts` is now only the `npcForSell` catalog lookup (the full acquisition resolver went with the planner layer).

## The fight solve (task 021)

`src/plan/bis.ts bestInSlot` searches the candidates `bisPools` gives (the owned or craftable pieces the character may equip; per slot the pinned extras, then the best by a heuristic against the monster up to the caps — the planner's 3/3 for `planRec`/`potionRec` and 6/6 for `fightRec`, the executor's 12/10). The objective (the header of `bis.ts`; task 025: feasible, admitted — p at the floor —, the expected seconds a win, then the tiebreak; below the floor by p); a set that loses still ranks by turns survived. **The search**: per weapon option (unarmed, the candidates, the worn one) a climb from empty slots with the weapon fixed — passes of one slot at a time, then the ring pair, the artifacts and the utility pair each chosen whole among their fillings, until a pass changes nothing; three seeded random starts (the same candidates give the same starts) climbed with the weapon free; on the caps' ladder (3/3 ⊂ 6/6 ⊂ 12/10) the answer of the step below — its candidates are the wider ones' top by the same order — as one more start (`LADDER`, `capPools`); the best end climbed again with the weapon free. **What it guarantees**, proven by `scripts/check-solve.mts` (in the plain gate, about 15 s): every answer is a **fixpoint** (no change of one slot, the weapon too, or of one group improves it), the caps are **nested** (6/6 never scores below 3/3, 12/10 never below 6/6 — 1,740 solves of the snapshots of 11-20 and 11-21), and on a **sample of 45 fights** (the wall World of report 021, the replay rows' highwayman, Third's ogre and bandit lizard of 11-22, the vampires of 11-20) the answer has the tier of the best set known (found once by a far dearer search; the check keeps the tiers). **What it costs**: a set's two fights (the expected one, the pessimistic one) are kept across solves — they read neither the price nor what is worn — as numbers in a table per monster and base stats (`makeEvaluator`, `FIGHTS_CAP` 500,000 rows of about 100 bytes, dropped whole at the cap); the candidates before the caps are built once per pool and character (`ownedPools`, `reach.ts uncappedOf`). The price: a solve is about 1.6 times the old one's (6/6 median 7.3 ms against 4.6 ms, no fight table); what the run pays is in report 021. **The planner's solves do not read what is worn** (`worn: false` from `reach.ts`: no `keep` tiebreak, no worn weapon option), so one pool gives one answer whatever is worn — but for the worn pinned artifacts (task 027g, C: `fightOptions` passes them as `BisOptions.fixed`, the first artifact slots of every set, in the solve key; play never takes one off, so the step's verdict is the solve's — the Sandwarden of report 027e, 76% solved without the Novice Guide, 47% with it); the executor's solves (`jobgear.ts`) keep the term (no swap for an equal piece at the bank).

## The fight simulator's effects

`src/sim/combat.ts` (`simulate`) models every solo-relevant combat effect (task 027: **restore potions** one entry each in slot order — the second fires only while HP is still under half after the first — and a worn stack with a quantity stops when it is spent: `EffectEntry.qty`, set by `stats.ts currentFighter` for a stack shorter than 50, a side's turns in a fight, so the executor's gate sees a short stack; the planner's solves pass none; `fightKey` carries it); `src/sim/effects.ts` (`MODELED`) is the audit list and records the reading taken for each one the docs leave ambiguous (2026-11-17: antipoison, corrupted, protective bubble, sun shield, greed, frenzy, enchanted mirror, void drain — plus poison/burn now land at the start of the BEARER's first turn). Only `christmas_magic` (no item or monster carries it) is unmodeled; ally-only effects are `SOLO_NOOP`. Hits are cached per side and recomputed only when an effect changes them (`dynamic`), and the turn mechanics are module-level functions (no per-call closures): ~2 µs per fight, half the pre-2026-11-17 cost — keep it that way, BIS searches and the atlas call it hundreds of thousands of times. Plain fights compute exactly as before. The fight-log check (`sim/validate.ts`) is the arbiter of those readings; `scripts/check-effects.mts` pins each mechanic on synthetic fights.

## Static catalog

`public/data/*.json` is a committed snapshot of the game's static data (items, maps, monsters, resources, npcs, …). `src/catalog/` loads it once into typed `Map`s and exposes sync lookups (`item()`, `monster()`, `mapAt()`, `tileAt()`, `itemName()`, …) that safely return `undefined` before load. `public/assets/` (map tiles + icons, committed) is served locally; most `<img>`s fall back to the CDN via `assetFallback`, **but map tiles in `MapView` have no fallback** — they must ship in the build or the map renders blank.

## Running

Local only — no deploy, no CI. `npm start` for unattended play (built UI, supervised service), `npm run dev` while editing. Both use port 5173, so only one runs at a time. The UI bundle ships no token (`.env` is read by the service only); the base path is always `/`. Shared engine code must not use `import.meta.env` (undefined under tsx) — `lib/devlog.ts`, `lib/util.ts` and `catalog/load.ts` were de-Vited for that; `catalog/load.ts` takes a disk reader from the service via `setDataReader`.
