# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A local client for [ArtifactsMMO](https://play.artifactsmmo.com/) (TypeScript + Preact, `@preact/signals` for state). **One Node service on this PC** (`src/server/main.ts`, run under `tsx`) runs the whole engine — queue runners, the hive, every call to the game API (`https://api.artifactsmmo.com`, Bearer token from `.env`) — and serves the browser UI, which is **only a view**. Moved off the browser tab 2026-11-05 after repeated Firefox tab OOM crashes; GitHub Pages was dropped.

## Commands

```bash
npm start          # vite build, then scripts/serve.mjs runs the service on http://localhost:5173/ (serves dist/)
npm run dev        # serve.mjs --watch: Vite (HMR) inside the service; engine .ts edits restart the service
npm run build      # UI production build → dist/
npm run typecheck  # tsc --noEmit
npm run assets     # bash scripts/download-assets.sh — re-download public/assets/ icons+tiles
node scripts/fetch-data.mjs       # new season: re-snapshot public/data/*.json from the live API
node scripts/fetch-map-assets.mjs # then fetch new map tiles (+ npm run assets for new icons)
```

There is **no test runner** in this project. Use `npm run typecheck` + `npm run build` as the correctness gate. To smoke-test the service without disturbing the real one, run it on a spare port with throwaway storage: `PORT=5199 node --import tsx --experimental-webstorage --localstorage-file=<scratch>/test.db --disable-warning=ExperimentalWarning src/server/main.ts` (it syncs once with the `.env` token; with no queues it makes no actions), then curl `/events` + `/rpc` or drive it with puppeteer-core.

**Dev forensics**: the service appends a trace of every API action (method, path, body, status), queue note change, head-item transition, activity-log entry, service start and failed rpc to `logs/dev.log` (gitignored; `src/lib/devlog.ts`, sink installed by `server/main.ts`; a per-process tag distinguishes service starts). Read it to debug runner behavior post-hoc — it is how the potion-brew bank livelock was caught.

## The local service: browser ↔ server split

The engine modules (`state/`, `api/`, `plan/`, `sim/`, `catalog/`) are loaded by BOTH sides — the browser for signals and pure helpers, the service for real — and `IS_SERVER` (`src/lib/remote.ts`, `typeof window === "undefined"`) decides what runs where. The rules:

- **The tab never runs the engine.** Runner modules hydrate from and persist to storage only `if (IS_SERVER)` (queue, hive, sim/validate); the hive observer effect is server-only (in a tab it would dispatch a second copy of every wave); `api()`/`getAllPages()` throw in the browser; the tab holds no token.
- **UI → server:** every engine function the UI calls starts with `if (!IS_SERVER) return rpc("name", [args]);` and its module ends with `expose({ name, … })`. In the tab the call becomes `POST /rpc {fn, args}` (it returns a Promise — UI callers must not use sync return values); on the server it is the real function, so internal callers keep sync semantics. `act()` in `api/actions.ts` is the one chokepoint for every action, so the `actions.*` the UI calls need no wrappers of their own. **A new UI-called mutator needs the guard + expose, or it silently runs against the tab's mirror.**
- **Server → UI:** `SYNCED` in `src/state/synced.ts` lists every server-owned signal the UI reads; the service sends a snapshot on `GET /events` (SSE), then each changed one (50 ms coalesced; flushed before every rpc reply). `connect()` (from `main.tsx`) mirrors them and loads the catalog. **A new server-owned signal the UI shows must be added to `SYNCED`; the UI must never write one** (the next push overwrites it — e.g. a claimed reward is dropped in `apply.ts`, not in the drawer). Pure UI state (`selectedCharacter`, `route`, `panelTarget`, `hiveProposals`, …) stays local.
- **Storage:** Node's built-in `localStorage` (`--experimental-webstorage --localstorage-file=.ammo/storage.db`, SQLite, ~10 MB quota), so the engine's persistence code is unchanged. Token: `.env` `TOKEN` seeds `ammo:v1:token` when none is stored. One-time migration: a brand-new service (no `ammo:server:imported` marker, no queues) accepts `importLocal` from a tab that still has browser-era `ammo:*` keys, then exits so the supervisor restarts it into the imported queues (`ammo:v1:migrated` in the browser stops re-imports).
- **Process:** `scripts/serve.mjs` supervises — restarts on exit with a doubling delay (1 s → 5 min; every start costs a boot sync, so a crash loop must not spin), exit code 3 (port busy) is final, `--watch` restarts on `src/**/*.ts` changes (`.tsx`/`.css` are Vite HMR only). The service binds `127.0.0.1:5173` BEFORE `boot()` (a second copy dies before it could run a second set of runners), exits when the supervisor's IPC channel closes (no orphans), and logs rather than dies on unhandled rejections. `/events` + `/rpc` reject non-local `Host`/`Origin`; `/rpc` requires `application/json` (cross-site requests need a preflight the service never answers) — whoever can call `/rpc` plays the account.

## The core invariant: one sync, then no polling

This is the whole design and the thing most likely to be violated by accident. Read `src/state/sync.ts` and `src/state/apply.ts` together.

- At service start (`server/main.ts` → `boot()` in `sync.ts`): restore from storage, load static catalogs from `public/data/*.json` into memory, then do **exactly one** authoritative read of `/my/characters`, `/my/bank`, `/my/bank/items`, `/events/active`, `/my/pending_items` (unclaimed achievement payouts → 🎁 topbar badge + claim drawer; a claim's echo updates state, `apply.ts` drops the row — no re-read), account.
- **Time-limited map events** (`/events/active` → `activeEvents` signal in `store.ts`, helpers in `src/state/events.ts`): fetched only in that sync; each event's expiration is enforced **locally** by the 4 Hz clock (no re-fetch). Event tiles overlay the static map everywhere — MapView drawing/hover/click, `liveTileAt`, `nearest()` in loopkit, and the queue's fight/gather pickers (`availableMonsters`/`availableResources`, tagged ⚡). New events appearing mid-session show up only after a manual Refresh.
- After that, **nothing polls.** Every action endpoint echoes the full authoritative `character` (and bank item moves echo `bank`), so `applyActionResult` (`src/state/apply.ts`) is the single chokepoint that folds responses into state — no GET-after-write. Re-sync only on the manual Refresh button (`reconcile()`).
- Budgets to respect: per-account **read** endpoints are the scarcest (~300/hr) — never add polling/GET loops. Actions are ~2000/hr; automation loops are paced by the cooldown each action returns, which keeps them well under.

`src/api/client.ts` is the only place that does `fetch` to the game API (the tab's only fetches are `/rpc` in `lib/remote.ts` and the catalog files). It handles 429 (rate-limit) and 499 (still-on-cooldown) retries, transient network failures (transport-level backoff, 2s→30s over ~90s, then a code-0 ApiError — which the queue runner holds-and-retries on instead of pausing), and pagination, and returns the unwrapped `data`. New API calls go through `api()` / typed wrappers in `src/api/actions.ts`, which route every response through `applyActionResult`.

## State

`src/state/store.ts` holds all dynamic state as `@preact/signals` (`characters`, `bankItems`, `bankDetails`, `selectedCharacter`, `panelTarget`, a 4 Hz `now` clock for cooldown countdowns, etc.). Components read signals directly and re-render automatically. `src/state/persist.ts` mirrors the durable signals to the service's `localStorage` (key `ammo:v1:state`) so a restart resumes instantly.

## The automation runner (the queue)

Exactly **one** per-character async runner executes everything: the **queue** (`src/state/queue.ts` + item vocabulary in `src/plan/queue.ts`), driven entirely by action cooldowns (`setTimeout` chains) — **it runs in the local service; closing the browser tab doesn't touch it.**

A queue is a user-editable ordered list of simple actions (move / fight ×N / gather ×N / craft ×N / withdraw / gear / accept-task / work-task / deliver / turn-in / …). `work-task` works whatever the CURRENT task turns out to be (unknown until accept-task runs): a bank-reset gear swap once per task (`geared` remembers it), then fight the task monster, or acquire the task item in the field — gather it, or gather materials + craft — handing bagfuls straight to the items master; task stock never moves through the bank (`deliver` is the from-bank-stock alternative) — EXCEPT at a dead end (`giveUpTask`: no field source, no winnable set): bank stock is handed over, then the task is **cancelled** for a tasks coin (fetched from the bank when not in hand), and only with no coin anywhere does the queue pause. `task-loop` chains accept → work-task → turn-in as ONE repeating item (×N tasks, 0 = forever) — `done` counts turn-ins, `geared` re-arms the bank-reset gear swap per new task. Fight, gather and craft items with a count of `0` run **forever** (craft ∞ = withdraw-a-bagful → craft → deposit cycles until the bank can't feed the recipe); a craft with `wait` (hive pipelining) holds and re-polls instead of pausing when bag + bank can't feed one run. Every item is skip-if-satisfied, so reloads resume mid-item; failure **pauses** the queue with the error on the head item — EXCEPT a missing map target (monster/resource/shop/workshop/master not on the map, e.g. an expired event): that **skips** the item with a log line (`skipItem`) so queues survive events ending. Multi-character bank races never pause either: a withdraw hitting 404/478 (a sibling took the stock first) drops the code from the local `bankItems` signal and re-plans next tick (`gearSwapStep` + `runStep` in exec.ts), and 461 (concurrent bank transaction) is waited out inside `api()` like a cooldown. Key `ammo:v1:queue`.

**Seasonal offerings (season 9, Seasonal Altar tile)**: the `offering` item does today's offerings — read `/my/{name}/offerings` once per character per UTC day (`todayOfferings`/`loadOfferings` in `src/state/offerings.ts`, cache `offerings` in store.ts, persisted, folded from accept/complete echoes in apply.ts — never polled), then at the altar accept every category (combat + 2 rotating skills) for the character's level bracket FIRST (the favor ×1.5 xp/drops boosts the farming), get each requirement (bank → favored target → field source, two craft levels deep; a craft offering never takes its product from the bank — banked gear is the fleet's), complete. A dead end skips that category for the day (`day`/`skip` on the item) instead of pausing; alone on a 🔁 queue a finished item holds for the next rotation instead of spinning. UI: Fleet 🛐 fold (`OfferingsSection`) + the altar drawer (`AltarPanel`, manual accept/complete). Game codes 574–577/598 are ≥ 500, which runLoop would treat as an outage — runOffering catches them itself.

**Per-character skill loops (2026-11-04, the main way to play; the hive is kept but frozen):** every character has up to two **pinned main skills** (`skillPins` in store.ts — click a row in the Skills card, 📌1/📌2, combat or any of the 8 skills, one more replaces the oldest; `craftPins()` hands the hive the first workshop pin). The `train` item levels a skill (`toLevel`, 0 = forever; `levels` = +N from the level it started at, `from` recorded on first run): **combat** fights the monster with the best XP per second (`trainingMonsterFor` in queue.ts: the docs' fight-XP formula `fightXp` in `plan/xp.ts` — level ratio + HP term, ×0.7 at 5+ levels above, zero at 10+, ×1.4 elite / ×2 boss — over 2 s/turn cooldown + rest-to-full, among monsters on the map the bank's best set beats; one BIS solve per candidate, memoized per bank reference + level; fed and gear-healed like a fight item; 📌 Train pins resets into the set vs the pick made at queue time), a gathering skill works the best node for the current level (re-picked per tick, `trainingResourceFor`), a workshop skill runs a self-contained loop in `runTrainCraft` — `trainRecipe` picks the recipe with the best **XP per fleet-second** (`src/plan/xp.ts`: the docs' crafting-XP formula — tier base by ITEM level, a √(ingredient count) multiplier, zero once the skill is 10+ above the item; cost = gather cooldown × drop rate per unit, a one-deep smelt of gathers, or a winnable drop fight at ~40 s × rate — `canBeat`, a bank-pool BIS solve memoized per bank reference — minus recycling's floor((n−1)/5)+1 random units back; an ingredient nobody can produce counts as free while bag + bank cover a run and caps the batch at that stock). The craft itself is ~5 s; materials are 99% of the time, so the model's whole point is XP per material unit and **every workshop recipe from Lv 10 up needs a monster drop** (feathers 1/8, slimeballs 1/10, cowhide/wool 1/12 — a drop costs about what a smelted bar costs). A batch is half a bag of DIRECT materials (6 bars per axe — a one-deep sub-craft is staged through the free half a bagful at a time, so 48 bars' 480 ore never has to fit at once), `sourceOne` fills a short ingredient (bank → gather → hunt, `fightGear` wears the bank's fight set → sub-craft), craft (weapon slot swapped to the best `<skill>_crafting` tool first — `craftGear`; it ping-pongs with the gathering tool as a bag-only equip because `trainKeep` holds spare tools), then recycle the product (or bank a non-recyclable one), repeat. **Automation never recycles a rare-ingredient product** (`autoRecyclable` in `plan/xp.ts`, 2026-11-09): recycling hands back random units, so a gem or tasks-coin crystal is mostly lost — an ingredient over `RARE_ACTIONS` (50) actions per unit from its cheapest source (best drop rate, a craft's ingredients summed, an NPC trade priced in drops; gold prices don't count) keeps the product banked for a manual decision, in the train picker (charged full materials), the train loop, the hive's level-skill batches and the recycling achievement. 157 of 257 recyclable recipes are gated that way (the whole jasper/astralyte tier), yet every craft skill keeps a common-only recipe at every level 1–50. The user's `recycle` queue item is untouched. `scripts/check-recycle.mts` asserts the split offline. **Helpers**: a `train` item with `for: <crafter>` ("help X train Y", the form's second select, or 🤝 **Fleet helps** = `queueAssist` puts one at the FRONT of every other queue and starts it) runs `runTrainAssist`: keep the bank two batches ahead on the crafter's CURRENT pick (the pick is fleet-aware — `helpersOf` = running queue heads helping that crafter, so a recipe only a helper can feed qualifies), produce one trip's load of the least-covered ingredient it can make (a bagful of raw smelted = 10 bars, at most a batch of a hunted drop — smelting never fills the bag, so a bigger load meant hours of bars riding in bags; finishing whatever is already in its bag first), deliver, repeat, never withdrawing; the crafter sources what it can itself and **waits** (15 s polls) for a helper-only ingredient instead of pausing. Fights in a train loop rest instead of eating (no food provisioning). A queue has a **🔁 repeat** flag (`QueueState.repeat`: a finished item goes to the back with its progress wiped; the hive clears it on dispatch so its ids can finish). **📌 Train pins** (`queuePinTraining`) builds the character's main task from the pins: per pin a bank-reset gear item + `train +1 level`, with 🔁 on, so the two skills level in turn forever.

These simple items are the **only execution vocabulary**. The old planner/campaign layer (goal compiler, task/train-craft phase machines, acquisition resolver) was removed 2026-07-06 — a planner must compile goals **down to queue items**, never run its own machinery. The hive (below) is that planner.

Stop semantics: ⏹ persists `running: false` IMMEDIATELY (a reload can never resurrect a stopped queue) while the loop drains its in-flight action — `liveLoops` covers that gap so ▶ during the drain just cancels the stop instead of double-launching. In dev the supervisor restarts the whole service on an engine edit (a hot swap would zombie the old runLoop); `queue.ts`/`hive.ts` still self-reload the TAB on HMR so its mirror signals stay single.

The runner pattern (copy it if a second runner ever returns): a `signal<Record<name, Job>>`, a module-level `stopFlags` Set, `step()` = run one action then `waitCooldownFull` (`src/state/loopkit.ts`), and the **reload-resume** pattern — the job signal is hydrated from its own `localStorage` key at module load, an `effect()` writes it back on change, and `resumeQueue()` (called from `boot()`/`login()` in `sync.ts` **after** the sync) re-launches. Hydrate before the persisting `effect` first runs or it overwrites the saved jobs — and both only `if (IS_SERVER)`. **Do not route runner persistence through `persist.ts`** (import cycle: `persist → queue → actions → apply → persist`) — the runner owns its key. Shared risky mechanics (bank-off, food-first healing, forecast gating, gear swaps) live once in `src/state/exec.ts`.

## The hive: the account-goal coordinator

The strategy layer above the queues — a **pure compiler + signal observer**, never a second execution engine. Domain in `src/plan/hive/` (pure functions over a `HiveCtx` snapshot: no signals, no API, no `state/` imports), runtime in `src/state/hive.ts`, UI in `src/ui/HivePanel.tsx` (🐝 topbar drawer + status strip atop the Fleet tab).

- **Propose → launch → observe.** `proposeGoals` enumerates + scores account goals (gear-upgrade / farm-tasks / achievement / level-skill) as value-per-hour (`score.ts` holds every tunable); a goal whose PLAN is partial is discounted (near-miss candidates alone don't halve it), and prerequisites are promoted as standalone goals scored as the parent's value over the combined wall-clock (`promoteBlockers`). Estimates: `SEC_PER_ACTION` is measured (~30 s), task cost comes from tasks.json sizes (`actionsPerTask`), parallel work converts to wall-clock per participant (`wallActions`). Two more kinds are built by the user in the drawer's builders and never auto-proposed: **craft-order** ("make me N of X" — the fleet gathers in parallel, the pinned/qualified crafter finishes behind a bank barrier; satisfied when the fleet OWNS the ordered quantities) and **earn-gold** ("earn +N gold", `plan/hive/gold.ts` — each participant works its best gold-per-action LANE: gather+sell / bounded task batches / fight+sell, ranked from live ctx; waves end in deposit-all so `ctx.bankGold` is fresh at the barrier, sell quantities stay provably coverable — guaranteed rate-1 drops plus bank stock claimed by ONE character per code — and it is satisfied when bank + participant pocket gold reaches the target). The user Launches one; the hive **takes over** all non-opted-out characters' queues (stop + clear, behind a confirm), then only ever writes queue items and watches the `queues` signal (one `effect` → microtask-coalesced `tick`).
- **Recompile-at-barrier is the core contract**: `compileGoal` returns waves but only `waves[0]` executes; when its assignments complete, the runtime re-calls `compileGoal` with fresh state and dispatches the NEW wave 0 — drop shortfalls become top-up waves, a consumer craft **pipelines** behind its producers in the same wave as a `wait` craft (holds and re-polls bag + bank instead of pausing on missing mats; `releaseStarved` drops one once no producer is left, so the barrier tops up), and skill training re-picks its recipe as the level rises. `HivePlan.once` (farm-tasks) means "wave done = goal done, no recompile"; an item-identical recompiled wave trips the **stall guard** (finish `incomplete`) — unless the plan's `progress` metric moved (earn-gold reports fleet gold there: a capped lane may honestly repeat the same batch while still earning; a zero-progress identical wave still stalls). Waves must contain **no infinite items** (they'd never complete) and ≤1 assignment per character — compile-side rules: mid-wave idle is rebalanced at **runtime** instead (`rebalanceWave`): a participant whose part is done (or who was never assigned, or who only holds on a starved `wait` craft — its slice is dispatched AHEAD of the craft via the hive-only `insertItem`, and it never gets a filler) first **steals** — `planSteal` carves half of the biggest running gather/fight lane they can work (a `times` patch on the victim's hive item via `patchItem`; a smelt chained right behind the gather moves with its ore in whole runs; never below `SPLIT_ACTIONS` × 30 s, never from a paused lane — slice and wave-tail sizes are SECONDS at each lane's measured pace (`lanePace`: elapsed since dispatch per fight/gather done, so eat/rest/food runs count; a wolf ran ~130 s, not 30), never a random-drop or two-deep chain) and gets the slice as a fresh barrier-holding assignment (ids in the `s<k>` namespace); only when nothing is carvable AND the wave's longest lane outlasts a gear reset (`FILLER_MIN_WAIT`) do they get an infinite items/monsters task-loop as a `filler` assignment (`fillerItems` in tasks.ts picks the master) — excluded from `waveDone`, item ids in the `f` namespace, dispatched only onto an empty stopped queue (user edits win), pulled (`pullFillers`) only when the run continues to a next wave so filler never delays the goal. A goal that ENDS (done/incomplete — not ⏹ stop) never parks the fleet (`moveOn`): the next **backlog** goal launches (user-queued via ＋ Queue; unlaunchable entries are dropped with a log line), else in **continuous mode** (⟳ chip, `auto`) the best proposal that compiles — minus labels that recently ended `incomplete`, so a stalling goal can't relaunch itself — else `handOffToTasks` gives every idle participant an infinite items task-loop as a plain user-owned item (fresh id, not `hive:*`). An auto-launch keeps user items on participants' queues (the hive appends behind them); only the manual Launch, behind its confirm, clears. ⏹ switches continuous mode off.
- **Dispatch is idempotent** via deterministic item ids (`hive:<startedAt>:<waveSeq>:<char>:<i>`): reloads re-attach instead of re-pushing, and a user deleting a hive item counts as done — the hive appends and watches; user edits win. Per-assignment status is **derived** from the queues signal (`assignmentStatus`: done = our ids gone, paused = error on OUR item, blocked = error on a user item ahead), never stored. A paused assignment holds its wave (others keep working) and gets Retry/Skip in the UI — no auto-retry.
- **Budget**: the hive itself performs ZERO API calls except one `loadAchievements()` per barrier for achievement goals (dynamic import of sync.ts keeps the static graph acyclic). `fleetBis` (ctx.ts) memoizes BIS searches per bank array reference with planning-grade pool caps; a cold `proposeGoals` is a 1–3 s synchronous sweep behind an explicit button.
- Follows the runner pattern: own key `ammo:v1:hive` (hydrate before the persisting effect, NOT via persist.ts), `resumeHive()` from `boot()`/`login()` **after** `resumeQueue()`, stop-sticks-first (`status:"stopped"` persists before queues unwind), HMR self-reload.
- `planAcquire`/`acquireWaves` (`plan/hive/acquire.ts`) is the rebuilt acquisition resolver — fleet-aware (gather → craft → fight → buy, candidates by skill/forecast, virtual-bank accounting, gather→smelt chains stay in one queue; every other craft pipelines in wave 0 on its preferred crafter as a `wait` craft, and a craft whose skill is PINNED to a specialist is never chained onto gatherers — the specialist gets the craft and its XP). Dead ends surface as `Blocker`s with a suggested prerequisite goal (small skill gap → level-skill, tasks_coin shortage → farm-tasks).

## The gear model: bank reset, bank-only sets

Gear is **never crafted or acquired for a character** — the bank is the single source of truth. Read `src/plan/jobgear.ts` (planner + stateless differ) with `gearSwapStep` in `src/state/exec.ts`.

- **A gear-managed job starts with a full bank reset**: go to the bank, deposit EVERYTHING (whole inventory, all pocket gold, every worn slot incl. utility potion stacks), then withdraw + equip the best set **available in the bank at that moment** (`jobGear`: fights via the bank-only BIS solver, gather/craft via prospecting/wisdom/tool argmax). Implemented as the `reset` mode of `nextGearAction`; the queue's `gear` item carries `reset: true`.
- **Fight sets include utility potions**: the BIS search covers the utility slots from owned stock (restore/boost potions change the forecast honestly — the live gate sees worn stacks via `currentFighter`). The differ equips whole stacks (game cap 100) and re-fills a slot from the bank when it drains empty; non-fight desired maps leave utility slots unmanaged, and a reset merges `RESET_UTILITY_STRIP` as an **underlay** so a fight set's potion picks survive while other jobs strip them.
- **Potions get brewed when the bank runs out**: `brewablePotions` (consumables.ts) lists potions the character could produce (alchemy skill + every ingredient stocked or gatherable); jobGear runs a second BIS solve with them as `extraCandidates` and adopts the set **only on a material forecast gain** (win-flip / safe-flip / fewer seconds per kill) — the solver's fills-a-slot tiebreak alone must never send anyone on a brew expedition. The BIS objective (`bis.ts`, `killSeconds`) is **seconds per kill** — fight cooldown (2 s/turn) + rest back to full (5 HP/s) — never HP remaining: a restore potion heals every turn under half health, so an HP objective rewarded a slow weapon that dragged fights out (2026-11-07: fire staff over iron sword vs cow); and potion-restored HP counts as lost too (`hpRestored` on the forecast — a proc burns a potion that costs far more to brew than 6 s of rest), because rest-to-full alone let the potion pin end-of-fight HP at half of max, so every +HP armor read as extra rest and the solver stripped body armor (2026-11-08). `provisionPotions` (exec.ts, called from the fight item and taskGear after the swap converges) then brews a small batch (`BREW_BATCH`, ~15 — a brew means the fighter is standing around instead of fighting, so batches stay minutes-sized; the next expedition runs when the worn stack drains dry) via the shared `produceOnce` machinery, and the next gear tick equips it.
- Mid-job bank trips (inventory full) deposit loot + gold but keep worn gear (`depositAll`/`bankOff`). A **swap ceremony standing on the bank tile sweeps the whole bag first** (deposit-all-before-equipping: everything minus `keep` + unmet wants, utility wants protected up to a full stack) — in the field the stow list stays junk gear only, and loot never earns a dedicated trip.
- **Per-iteration self-heal**: fight/gather rounds re-derive the desired set from the live bank signal (memoized per bank reference — free until a bank echo changes it) and swap when something better appears.
- **Between-fight food is self-provisioned** (fight / work-task / task-loop items, `food: false` on a fight item opts out): a hurt fighter eats the best food in hand (`healOnce`), and when the hand runs dry `provisionFood` (exec.ts, plan side in `src/plan/consumables.ts`) sources more — withdraw the best stocked bank food, else **cook** the best recipe the stock can feed, else **gather** the raw materials in the field and cook them; batch sized by the fight forecast's expected HP loss (capped at ⅓ bag). Infeasible ⇒ falls back to rest — food never pauses a queue. Carried food + its ingredients ride the `keep` list so bank-offs and gear resets don't stash them; the task deliverable is never eaten.
- **Pinned artifacts** (`PINNED_ARTIFACTS` in jobgear.ts, currently `novice_guide`): once owned, every job set of a character that meets its conditions (novice_guide: level ≥ 10) includes one, and a worn copy is NEVER removed — the differ drops its slot from management entirely (even under a reset/stripAll), so it survives all swaps. Spare copies still deposit. Also: artifacts must be DISTINCT (game rule, 485 "already equipped") — jobGear's argmax and the differ both dedupe artifact codes.
- **Fleet gear coverage** (🛡 topbar drawer, `src/ui/GearCoveragePanel.tsx` over pure `src/plan/coverage.ts`): a read-only "virtual bank reset for everyone at once" — slot-groups × characters matrix of the level-best owned set each character would get from shared stock (item-level ranking, zero fight sims; tools and utility slots excluded, pinned artifacts stay with their wearer), plus missing-copy shortages (have/need; rings count ×2) and nobody-can-fill slots. The Sim playground's 🏦 "Best in bank" button is the fight-side sibling: the same owned-pool BIS solve the gear reset runs, for a chosen monster.
- `src/plan/acquire.ts` is now only the `npcForSell` catalog lookup (the full acquisition resolver went with the planner layer).

## UI layout

**A table-first check-in console (2026-11-04)** — the game isn't real-time, so the home screen answers "is everyone working, what's next, what needs me", and catalog data lives in sortable tables, not spatial drawers. `app.tsx` waits for the service's first snapshot + catalog (`catalogReady`), gates on auth (`TokenGate` — the token goes to the service) then renders a top bar of **tabs = hash routes** (`route` computed in store.ts: `#/fleet` default · `#/char` · `#/bank` · `#/items` · `#/monsters` · `#/achievements` · `#/map` · `#/sim`; `go(tab)`, `openCharacter(name)`), one `.tab-page` below. **Everything lives in a tab** — no drawers left except the Map tab's building drawer and the pop-up map; the top-right holds only Refresh / Sign out. Beside the tabs, outside them, the always-on **activity panel** (`ActivityPanel` in `ui/ActivityLog.tsx`): each character's live queue note, then the `log` feed; "Hide ›" collapses it to a thin edge strip (state in localStorage `ammo:v1:ui:activityHidden`).

- **Fleet** (`ui/FleetView.tsx`): "Needs you" (paused queues → Retry, stopped/idle characters → Run / 📌 Train pins, unclaimed rewards → Achievements tab, live events → Show on map), the Characters table (status, doing-now + progress via `itemProgress` from QueuePanel, up-next, main skills, bag, task, where), a characters × skills grid (click a cell to pin/unpin), then collapsible `Fold` sections that mount their body only while expanded: ⚔ **Group fight** (`ui/GroupFight.tsx`, `groupFightOpen`: pick a boss + up to 3 characters → 🛡 Prepare puts a `prepare` queue item at the front of each picked queue and starts it — one bank reset into the best set vs the boss (utility potions included, `provisionPotions` brews missing ones), walk to it, rest to full, then the runner STOPS the queue (never re-appended by 🔁) — then ⚔ Fight = one `actions.fight(leader, participants)`; the echo's `characters[]` updates everyone; group fights skip the 1v1 sim validator), 🐝 **Hive** (`HiveSection`; `hiveOpen` = expanded, the `HiveStrip` click expands it) and 🛡 **Gear coverage** (`GearCoverageSection`; `gearCoverageOpen`). The table itself is signals only — zero API calls; the 4 Hz leaves are `CooldownRing` / `EventTimer` only.
- **Achievements** (`AchievementsTab`): pending rewards (claim with the selected character) on top, then achievement progress — fetched once when first shown (a read), then only on ↻; the tab label carries the unclaimed-rewards badge.
- **Character** (`CharacterPanel`): switcher pills, a summary strip (+ `ActionBar` Walk/Enter), then a 2-column `.ws-grid`: the Queue as a numbered table (the running head shows the runner's live `note`) | equipment list (empty slots collapsed to one line) / skills table with Pin buttons / inventory. A character is always selected (`sync.ts` defaults to the first).
- **Bank** (`ui/TableTabs.tsx`) is deliberately NOT a table: a compact tile grid (several stacks per row — icon, name, qty, sell value, recipe uses; hover = item card) grouped Consumables / Currency / Equipment / Resources, with search + a sort select.
- **Items / Monsters** (`ui/TableTabs.tsx`) use **`ui/DataTable.tsx`** — the one table component (CSS-grid tracks per column, sortable headers, search box, toolbar slot, per-row `detail` line, optional `pageSize` + "show more"). **Items** is the whole catalog in one table — recipe with bank stock per ingredient, can-make, best crafter (pinned first), NPC buy offers and best sell offer with reachability — filtered by source (craftable / NPCs sell / NPCs buy / in bank), type, craft skill; hover any item for its full `ItemPopup` card. Acting on a row = append a queue item to a chosen character (`QueueTo`: craft ×N, fight ×N); tile-bound one-off actions (withdraw/buy/craft by hand) stay in the Map tab's building drawer. Monsters shows a current-gear `simulate()` verdict per character (memoized per characters echo); 🏦 "Best" runs the bank-owned BIS solve for that one monster on demand (never all rows — it's the slow path). `WhereCell` (inline) = static tile (click → `focusTile` + Map tab), else ⚡ live-event countdown, else "event"; 🔒 from `tileGate`.
- **Map** tab: `MapView` full size + an `EventsPanel` column while events are live. `CatalogPanel` (open on clicking a workshop / NPC / **bank** / tasks tile — branches on `panelTarget.type`) is a non-modal drawer over the map; Escape closes it. A `focusTile()` issued while no map is mounted is applied when one mounts (module-level `consumedTileFocus`); a mounting map centers on the selected character.

Moving a character by hand: the 🚶 Walk button (`ActionBar`) arms `moveMode` — the next map click moves the character — and the drawer offers "🚶 Send \<selected\>" when nobody is on its tile. Off the Map tab, an armed `moveMode` / `tilePick` ("Pick on map" in queue forms) pops up `MapPickOverlay` (app.tsx) so the asking form keeps its state. **Access-gated tiles** (`maps.json access.type === "conditional"`, e.g. the Tasks Trader behind the Tasks Farmer achievement): `src/state/access.ts` resolves the gate + whether it's met (from the on-demand `achievements` signal; `null` = unknown, the server stays the judge — never hard-block on it). The inspector and drawer show a 🔒 requirement line (the drawer lazily fetches achievements to color it), and `actions.move` rethrows the server's bare "conditions not met" with the requirement spelled out.

## Static catalog

`public/data/*.json` is a committed snapshot of the game's static data (items, maps, monsters, resources, npcs, …). `src/catalog/` loads it once into typed `Map`s and exposes sync lookups (`item()`, `monster()`, `mapAt()`, `tileAt()`, `itemName()`, …) that safely return `undefined` before load. `public/assets/` (map tiles + icons, committed) is served locally; most `<img>`s fall back to the CDN via `assetFallback`, **but map tiles in `MapView` have no fallback** — they must ship in the build or the map renders blank.

## Running

Local only — no deploy, no CI. `npm start` for unattended play (built UI, supervised service), `npm run dev` while editing. Both use port 5173, so only one runs at a time. The UI bundle ships no token (`.env` is read by the service only); the base path is always `/`. Shared engine code must not use `import.meta.env` (undefined under tsx) — `lib/devlog.ts`, `lib/util.ts` and `catalog/load.ts` were de-Vited for that; `catalog/load.ts` takes a disk reader from the service via `setDataReader`.
